# admin

Settings, a health view, and profile Save/Load, following [contracts/admin.md](../../contracts/admin.md) and [contracts/profile.md](../../contracts/profile.md). Python (Starlette) on the kit; settings and the profile record live in Postgres, per tenant.

## What it does
- **Per tenant** ([0013](../../docs/decisions/0013-multi-tenant-core.md) item 18, [contracts/tenants.md](../../contracts/tenants.md)): settings and the profile belong to the event (tenant) of the request's hostname, which the kit resolves through the tenants module (`CANCCU_TENANTS_URL`). Their API (`/api/admin/settings/…`, `/api/admin/profile`) and pages (`/admin/settings…`, `/admin/profile…`) answer 404 `not_found` on a host that is no tenant's, the platform's own hostnames included. Everything else (health, the session API other modules call on `admin:8080`, sign-in, people, the health view) stays outside tenant resolution until the central sign-in (#52) binds sessions to a tenant. The tables `admin_tenant_settings` and `admin_tenant_profile` (`migrations/`) are under row-level security, and every query runs as the role `canccu_admin_app` inside the kit's `tenant_transaction`. The single-event tables `admin_settings` and `admin_profile` are gone (`migrations/003_drop_single_event_tables.sql`). In IP mode (`CANCCU_IP_MODE=demo`, version `dev`) admin serves the demo tenant on an IP-literal host while the tenants module does.
- **Settings:** `GET`/`PUT /api/admin/settings/{module}` with `settings_version` concurrency and the `admin.settings.changed` event on the tenant's stream. A module reads its own settings on `GET /internal/admin/settings/{module}?tenant_id=` and sets some of its own keys on `PATCH` of the same path (signed by the module itself, `actor_user_id` in the event), for settings its contract makes the same values as something it stores. Forms are generated from each module's *declared* settings: one file `declarations/<module>.yaml` (format in `src/canccu_admin/declarations.py`), whose `groups` put every setting in exactly one card of the form and are the settings answer's `groups`. Pages: `/admin/settings`. A part's form (`/admin/settings/<module>`) shows each changed field's saved value ("Was 45.") and a save bar ("1 change not saved", Undo, Save) at the window's foot, on a phone above the bottom bar and out of the way while the page scrolls; `static/settings.js` saves without leaving the page, so a save that fails keeps the change ("Couldn't save", *Save again*). Without the script the form posts as before, and a refused save or a conflict answers the form again with what was typed; after a conflict only the fields the user changed (against the `was.<key>` values the form posts) keep what was typed, and the rest show what is saved now.
- **Health view:** admin checks itself and every module in `CANCCU_HEALTH_TARGETS` (`agenda=http://agenda:8080/health,...`) every 10 seconds (`src/canccu_admin/health.py`); Screen's `render` check is the part *Screen rendering*, since screen-render has no network. `/admin/health-view` shows the latest check: count tiles, then every part by name with what it does, a status badge, what it says with a way on ("What to check", "Open devices"), its version, answer time and log name, trouble first, and follows the checks while it is in view (`static/health.js` swaps in the tiles, the parts table, "Last check" and the menu's Health note without a reload, keeping an open "What to check" open); *Check now* checks at once (checks asked while one runs share it) and returns to the plain page, so a reload does not check again. Every admin page's menu says when a part needs a look ("Health 1 slow"). The latest check is a per-container cache, never state: a new container checks for itself, and only the "since" of a part that is down starts over.
- **Profile:** the profile lives in the tenant's event folder (`<CANCCU_FILES_ROOT>/<tenant>/admin/event`, by default `/files/<tenant>/admin/event`: `profile.yaml` + `assets/`); `admin.profile.saved` and `admin.profile.loaded` go to the tenant's stream. *Save* writes the current profile (record in Postgres plus stored settings) there; *Load* reads it, upgrades older versions step by step, validates it against the schema, applies it, and **warns about any file it names that is missing**. `GET`/`PUT /api/admin/profile` do the same as a zip; there a missing file is an error, as in the contract. `GET` builds its zip aside and leaves the event folder as it is, so downloading the current profile never changes what *Load* loads. The page `/admin/profile` shows what is loaded, when and by whom (`migrations/007_profile_loaded.sql`), with *Download this profile*; *Load* (`/admin/profile/load`) and *Upload* (`/admin/profile/upload`, a zip as *Download* makes it) each ask first, saying what is replaced and kept and offering the current profile for download, before they replace anything. A `profile.yaml` in the event folder that can't be loaded (bad YAML, not UTF-8, not the schema, too new) says why on the page and in Load's question, and Upload stays.
- **The profile's design for theming:** `GET /internal/admin/profile/theme` and `/internal/admin/profile/logo` (`?tenant_id=`, on `admin:8080`) answer the profile's `theme` and the bytes of `logos.main`, for theming's revision 0. Only theming's service identity may call them, and only for an event the tenants module knows. An import announces `admin.profile.loaded` only after the new files are in the event folder.
- **Sign-in:** `/admin/sign-in` runs Discord OAuth2 (scope `identify`, `state` bound to the browser by a short-lived `canccu_sign_in` cookie, PKCE). The redirect URI is `CANCCU_PUBLIC_URL` + `/admin/sign-in/callback`; absolute URLs never come from the `Host` header. `CANCCU_PUBLIC_URL` is normalised at start (lower-case scheme and host, no default port, no trailing slash) and refused with a clear message if it is not a plain http(s) URL. Each sign-in starts a new session; the opaque cookie `canccu_session` (HttpOnly, SameSite=Lax, host-only, Secure when `CANCCU_PUBLIC_URL` is https) names a row in Postgres, stored as a hash. A session ends after 4 hours idle or 24 hours in all. `/admin/sign-in?next=<path>` comes back to that path after signing in (the check-in page, #227): only a path on this site (no scheme or host, no `//`, no backslash, printable ASCII, at most 1,024 characters), kept with the flow's `state` in Postgres and never read from the callback URL; anything else goes to `/admin/` as before. `GET /api/admin/session` and `POST /api/admin/session/sign-out` follow the contract (sign-out answers 204 and clears the cookie whatever state the session is in). The session's `superadmin` is `false` for every session until the central sign-in (#52): admin's sessions are bound to neither the platform nor a tenant, and nothing tells admin who is a superadmin yet. A session that ends (sign-out, expiry, a new sign-in) leaves admin's own rights cache at once. Pages send a signed-out browser to sign in, send a signed-in user with no role at all to the sign-in page's "No role yet" card (with Check again; agenda's, notify's, Screen's and theming's organiser pages do the same), show one with a role but without the page's right a page explaining to ask the owner, and show only the links the user may follow (#440, sheets 3 and 8). The sign-in page says "Sign in to look back" for an archived event, offers Check again and the words to pass on while Discord is not set up, says "Discord was closed before it said yes" when a cancelled flow comes back through another module's page (its `next` carries `signin=cancelled`, which the card drops), and says "You were signed out" (and clears the cookie) to a browser whose session ended by itself. Its Privacy tag leads to `/notify/privacy`. `/admin/offline` is the "You're offline" page: `static/sw.js`, a service worker every signed-in organiser page registers (`static/shell.js`, loaded by the kit's shell) for the whole site (`Service-Worker-Allowed: /`), passes every answer through and shows the cached offline page, in the person's shell and kept with the stylesheet and script it links, only when an organiser page cannot be reached; signing out clears it (`Clear-Site-Data: "cache", "storage"`: Cache Storage holds the copy, and the worker is registered again on the next signed-in page); a state-changing request from another origin is refused by the kit (403 `origin_refused`, with a correlation id), and a page POST whose origin is not `CANCCU_PUBLIC_URL` by admin itself (403 `bad_origin`).
- **First-run code:** while there is no owner, every start logs a new one-time code (`first-run code: XXXX-XXXX-XXXX`, in `docker compose logs admin`). Enter it at `/admin/first-run` and sign in with Discord: that account becomes the owner, and the code is used up. A restart replaces an unused code.
- **Rights:** two roles. The owner holds every admin right; an admin holds them all except `admin.rights.write`. Everyone who signs in gets a session; without a role it has no rights. The owner makes people admins on `/admin/people` (#437, sheet 4): search, a role filter, each person's Discord handle and "Last here" (`migrations/006_people.sql`), 25 at a time with "Show N more"; a role applies at once with Undo in the notice, and emits `admin.rights.changed`. Remove asks first, then ends the person's sessions and takes their role (`admin.rights.changed` with no rights, which also drops every module's cached answer); the person stays in the history, and signing in again brings them back without a role. On a phone a row opens the person's sheet (`/admin/people/{id}`). "Copy the sign-in link" (`static/people.js`) copies `/admin/sign-in` on the page's own hostname. Admin checks its own pages through the kit's `RightsChecker` against `CANCCU_ADMIN_URL`, like every module.

## Environment
The kit's `CANCCU_MODULE`, `CANCCU_VERSION`, `CANCCU_VALKEY_URL`, `CANCCU_ADMIN_URL`, plus `CANCCU_DATABASE_URL` and `CANCCU_TENANTS_URL`; optional `CANCCU_FILES_ROOT` (default `/files`), `CANCCU_SIGNIN_HOSTNAME` and `CANCCU_SUPERADMIN_HOSTNAME` (never a tenant), `CANCCU_IP_MODE`, `CANCCU_HEALTH_TARGETS`, `CANCCU_CONTRACTS_DIR`, `CANCCU_DECLARATIONS_DIR`, `CANCCU_MIGRATIONS_DIR` (the image sets it). Sign-in needs `CANCCU_PUBLIC_URL`, `CANCCU_DISCORD_CLIENT_ID` and `CANCCU_DISCORD_CLIENT_SECRET` (`deploy/.env`); without them admin starts, logs the first-run code and says on `/admin/sign-in` that Discord sign-in is off.

## Check
```sh
pip install -e ".[dev]" && ruff check . && ruff format --check . && mypy . && pytest
```
The tests use in-memory stores, a fake Discord, a fake tenants registry and round-trip `events/demo/`; `tests/test_tenancy.py` holds the cross-tenant leak tests of every settings and profile path. With `CANCCU_DATABASE_URL` set (`deploy/compose.test.yml`; CI's `module (admin)` job) `tests/test_auth_store.py` also runs the sign-in store against Postgres, and `tests/test_store_pg.py` the settings store, its migration, row-level security and the leak test; without it those are skipped. `tests/test_store_pg.py` empties the settings tables, so it refuses a database whose name does not end in `_test` ([docs/ci.md](../../docs/ci.md#modules)).
