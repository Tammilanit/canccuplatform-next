# agenda

The agenda module serves [contracts/agenda.md](../../contracts/agenda.md): the run-of-show of each event (tenant), its own list of kinds, and now and next. Plan and split: [docs/plans/issue-187.md](../../docs/plans/issue-187.md). Package 1 (#187) built kinds, adding, editing and moving items, reading, and now and next; package 2 (#210) adds delay with following, cancel, remove, the reminder scheduler and the tournament-session mirror. Package 3 (#211) adds the run-of-show pages; #212 adds announce, undo and concurrent edits. Clone follows the tenants series API (#150).

## How it works
- **Tenancy:** each request's event comes from its `Host`, through the kit's `TenancyMiddleware` and `TenantResolver` (`CANCCU_TENANTS_URL`). Every table is per tenant under RLS; requests run as `canccu_agenda_app` (`SET LOCAL ROLE` inside each transaction).
- **First use:** an event's counters (`agenda_version`, `kinds_version`) and the starter kinds are made in its own context on its first agenda request. No job walks every tenant.
- **Writes:** one transaction per write takes the event's counter row `FOR UPDATE`, so `agenda_version` and `kinds_version` never skip or repeat. Its bus events go through the kit's `Outbox`: stored in `agenda_outbox` in the same transaction and sent after the commit, so a committed write never loses an event and a refused one sends none (#288). A send that fails (Valkey down) is retried by a loop in every container, every 2 seconds, which visits the events listed in the global `agenda_outbox_tenants`; delivery is at least once, with the same event id.
- **Who reads what:** guests read `public` items when the event's info-page mode lets them; any valid session on the event's hostname also reads `attendees` items until the tenants membership API lands (#150; `access.is_member`); `agenda.crew.read` adds `crew` items.
- **Archived events:** writes get 409 `event_archived`. The status comes from the resolver's tenant context, which the module drops on every tenants event.
- **Delay** with `following` checks every shifted item before it writes any, so a refused shift moves nothing. Each shifted item gets its own `agenda_version` and its own `agenda.item.delayed`, all with one `correlation_id`, in order of the new start.
- **Quiet changes** (#388): a delay or an edit may say `announce: false`; its `agenda.item.delayed` or `agenda.item.changed` carries it (every event of one shift the same), so no consumer announces it, and the screens still show the new times. Its undo is quiet too.
- **Timers** (`timers.py`): every write rewrites its items' rows in `agenda_timers` (reminders at each lead in effect, the start and the end) in the same transaction. A fired reminder is recorded in `agenda_reminders_fired` and fires again only for a new start ahead set by an announced delay, edit or session move; the record stays, so no other write (a quiet change, a kind, the lead-time setting) arms it again unless a reminder for that lead is still pending. A pending one still moves with the item. A loop in every container, every 5 seconds, visits the events listed in the global `agenda_timer_tenants`, claims due rows with `FOR UPDATE SKIP LOCKED` and stores their events in the outbox in the transaction that deletes them. A reminder whose start has passed (after an outage) is dropped; starts and ends still fire. A change of the lead-time setting (`admin.settings.changed`) or of a kind reschedules the items it touches.
- **Tournament sessions** (`mirror.py`): `tournament.session.*` events, read from the start of each stream, keep one item per session. `agenda_sessions` holds the newest session revision applied and the tombstone of a removed session, so a late or replayed event changes nothing. The tests feed fixtures (`tests/fixtures/tournament/`) that `tests/test_fixtures.py` checks against the event catalog.
- **Pages** (`/agenda/`, Caddy strips the prefix; in admin's "Event" menu): server-rendered, phone-first, with no script. The run of show by day as sheet 5 of `docs/design/mockups.html` draws it (`pages.py`, `day_view.py`): what is on now (or next) with its delay buttons and "Show on screens now", and from 1440 px the main zone's live screen beside it (screen's own player of the zone, for a session with `screen.devices.read`); the day switch and "Jump to now"; the day as one list (time, the planned time a delay moved, the item and its kind, where, for whom), now marked; and one item with its actions, which a row picks through `?item=`: beside the list from 1440 px (by default the next item), over the day below that, with a Close; the full item form, where a move shows its preview first and an edit has the same "Tell people" choice (`item_pages.py`); delay (only this item by default, "Also move the N items after it" as an option, and "Tell people (Discord, phones)", ticked by default, as the accepted design #382 draws them; its confirm, drawn once per combination of the two choices, follows the ticked boxes through the stylesheet, with no script, in rows as sheet 5 of `docs/design/mockups.html` draws them: Starts, Also moves, Screens, Discord, Phones, and a button that says what it does; `delay_pages.py`), cancel and "show on screens now" (a delay that brings the item forward to now), each with a preview of what moves, what does not and why, and who is told on which channel (`edit_pages.py`, `preview.py`); quick-add in a few taps (`quickadd.py`); and templates (`templates.py`, `template_pages.py`). Previews use the same `edits.plan_delay` as the change; a delay's confirm carries the `agenda_version` it was shown at and shows the preview again if the agenda changed meanwhile. Templates are page data, not in the API: a new event gets Food, Ceremony and Game session. Sessions need `agenda.items.write` (or `agenda.crew.read` to look); a signed-out browser goes to `/admin/sign-in?next=<this page>` and comes back to it with its query (after a form post, to the form's page, or to the list where there is none, as after an undo or a delete; a return path admin would drop, over 1024 characters or not printable ASCII, also goes to the list); the pages use the stable classes of `packages/ui` and serve its `ui.css`.
- **Announce** (`announce.py`): `POST /api/agenda/items/{id}/announce` emits `agenda.item.announced` with the current `agenda_version` and changes nothing. "Show on screens now" offers it in the same step: the item is brought forward first, then announced, so the event carries its new times; a running item can still be announced.
- **Change log** (`agenda_changes`, written by `store.insert_item`, `update_item` and `delete_item`): one row per revision of an item, with who (a person, or the tournament module), the fields and their old and new values. The item page lists the latest changes.
- **Undo** (`inverse.py`, `undo.py`, table `agenda_undo`): each page change (add, quick-add, edit or move, delay, cancel, show-now) records its inverse inside its write. For 2 minutes its author gets an Undo button; it runs through the normal writes (people who were told are told again), is used once, and is refused, naming who, when an item it would touch has changed since. A cancel is undone by a new item with the same fields, since cancelling is final; an announcement cannot be taken back.
- **Concurrent edits** (`merge.py`): an edit form sent at an old revision is re-applied on the current one when none of the organiser's changes touch a field changed since (from the change log); otherwise the page shows who changed what and the form as the item is now. The API keeps 409 `version_conflict`.
- **For modules** (`internal.py`): `GET /internal/agenda/items?tenant_id=` serves every item of an event, crew and cancelled ones included, to a module keeping its own copy (screen). It skips tenant resolution (the caller's host is `agenda:8080`); the kit's service identity guards it and `TenantResolver.by_id` finds the event.
- **Settings** (`reminder_leads_minutes`, `notify_channels`, declared in `modules/admin/declarations/agenda.yaml`) come through the kit's `SettingsClient`; `notify_channels` in effect is the item's choice, else its kind's, else the event's.

## Environment
`CANCCU_DATABASE_URL`, `CANCCU_TENANTS_URL`, plus the kit's `CANCCU_MODULE`, `CANCCU_VERSION`, `CANCCU_VALKEY_URL`, `CANCCU_ADMIN_URL`, `CANCCU_SERVICE_KEY`. Optional: `CANCCU_MIGRATE_DATABASE_URL` (the migration role; without it the login role migrates, as in the tests), `CANCCU_SIGNIN_HOSTNAME`, `CANCCU_SUPERADMIN_HOSTNAME`, `CANCCU_IP_MODE=demo` (only with version `dev`), `CANCCU_TRUSTED_PROXIES`, `CANCCU_UI_CSS` (the path of `packages/ui/ui.css`; the image sets it).

Through Caddy: `/api/agenda/health`, the contract's `/api/agenda/…` paths, and the pages under `/agenda/` (`/agenda` redirects there, keeping its query). Not through Caddy: `/internal/agenda/…`, for modules on the stack's network, and the internal paths, the API and health under the pages' prefix (`/agenda/internal/…`, `/agenda/api/…` and `/agenda/health` are 404).

## Check
```sh
pip install -e ".[dev]" && ruff check . && ruff format --check . && mypy . && pytest
```
The tests need a real Postgres, because RLS cannot be faked; without `CANCCU_DATABASE_URL` they are skipped. They empty the module's tables, so they refuse a database whose name does not end in `_test` ([docs/ci.md](../../docs/ci.md#modules)). They include the cross-tenant leak tests (`tests/test_leak.py`). CI runs them in the `module (agenda)` job ([docs/ci.md](../../docs/ci.md#modules)):
```sh
docker compose -f ../../deploy/compose.yml -f ../../deploy/compose.test.yml up -d --wait postgres
# canccu_test is made once, as in docs/ci.md#modules (Locally)
CANCCU_DATABASE_URL=postgres://canccu:canccu-local-only@127.0.0.1:5432/canccu_test pytest
```
