# pizza

The pizza module serves [contracts/pizza.md](../../contracts/pizza.md): the event's group food orders, their lifecycle and rights, pizzerias and menus, money on the order, the menu CSV and the export for the payment system (#117, the [step 5 plan](../../docs/briefs/step-5-pizza.md#plan)). The scheduler and the holder's and crew's pages are #118's; the attendee's pages and their live stream #119's, and the `food` topic it registers with Notify #643's.

## How it works

- **Tenancy:** each request's event comes from its `Host` (the kit's `installTenancy`). Every table is per tenant under RLS; work runs as `canccu_pizza_app`. The global `pizza_tenants` lists the events pizza has served (a deleted user is forgotten in each) and `pizza_outbox_tenants` the events with unsent events.
- **The lifecycle** (`lifecycle.ts`, `items.ts`): an order is a row in `pizza_orders` from open to done or cancelled. Every step is one conditional `UPDATE … WHERE state = ANY(…)` in the request's transaction, which also reads what the row was (`FOR UPDATE`): of two racing requests one changes the row, the other finds it moved on and is told why (`conflicts.ts`), or, for a step already taken, gets the order back without a second event. Opening is serialised per event by an advisory lock (the event's count and the day's numbers); a pizza's write first bumps its order's revision, which takes the order's row lock and checks its state in one step. Partial unique indexes back one open order per pizzeria and one held per person. `scheduled()` is the module's own steps (actor null) for #118's scheduler.
- **Idempotency** (`idempotency.ts`): every write carries an `Idempotency-Key`; its row is written in the write's transaction, so a retry waits on the first and reads its answer (E2).
- **Events** (`events.ts`): stored in `pizza_outbox` in the write's transaction and sent after it commits (the kit's `Outbox`; a loop resends what a failed send left, every 2 s). The Person's Discord id comes from `GET /internal/tenants/users/{user_id}`, cached a few minutes; `null` when the tenants module does not answer (E13).
- **Rights and visibility** (`policy.ts`, `views.ts`, `present.ts`): `authorize(action, caller, facts)` lists every action of step 5 with who may take it and through what; a crew right counts only where admin is reachable. Each read is drawn for its caller: a guest, a member or the holder and crew (D9). Membership is read in `people.ts`; until the tenants module serves it (#150) every signed-in session on the event's hostname counts, as in agenda and notify.
- **Menus** (`menus.ts`, `menu-csv.ts`, `validate.ts`): one plan for the JSON menu, the menu CSV and the profile; the preview runs it without writing.
- **Money** (`money.ts`, `money-routes.ts`, `money-view.ts`): each person's amount by the largest remainder; changes once an order is closed are audited and tell the people whose amount moved. A confirmed receipt read sets the total and every price in one `PATCH` (`prices`, `receipt_id`).
- **Settling to the payer** (`paid.ts`): the holder's Paid ticks and the payer's "Pay me with" (a MobilePay number, an IBAN checked by its digits), in the API only; each person sees their own amount, mark and the payer's details (`views.ts`).
- **Receipts** (`receipts.ts`, `photos.ts`): photos in the files volume under `/files/<tenant>/pizza/receipts/`, re-encoded upright at most 2,576 px so their metadata (a location) is gone; the photo body is read by pizza's own parser so 413 and 415 carry the contract's codes. The anonymisation and a deleted event remove the folder.
- **The AI reader** (`reader.ts`, `reader-key.ts`, `reader-routes.ts`, `receipt-match.ts`, `anthropic-reader.ts`, `fake-reader.ts`): one small interface; Claude Haiku 5.5 through the Anthropic SDK with a structured answer, 20 s and no retries. The provider key is sealed with the kit's `SecretBox` (bound to the event) and set in Admin → Integrations; a read counts against the event's daily reads in a transaction of its own, so a failed read still counts and a refused key stops the reader. A receipt read is kept on the receipt as a suggestion matched to the pizzas; nothing changes until the holder confirms.
- **The record and the export** (`record.ts`, `export-csv.ts`, `record-routes.ts`): flags by kind, edits after call-in counted from the history; **privacy** (`privacy.ts`, `consumer.ts`): the export and delete, the 12-month anonymisation, deleted users and events, a member who left, clone.
- **Audit** (`audit.ts`): entries go to the tenants module in the request that made the change, before it commits.
- **The scheduler** (`scheduler.ts`, `due.ts`): every container ticks every 30 s (and once at start) through the events pizza serves. A tick writes each live order's due steps into `pizza_due` from the order and the event's settings, then takes the due ones one at a time `FOR UPDATE SKIP LOCKED`, checks each again against the order, takes it (the lifecycle's `scheduled()` or a reminder) and marks the row sent in the same transaction, which stores the events in the outbox. Reminders go to one person each (`pizza.reminder.triggered` with `user_id`); "the crew" is `pizza_crew`, the members whose session showed `pizza.order.manage` when they last used pizza (`http.ts`, `whoIs`). `/health` has the check `scheduler` with its lag.
- **The attendee's pages** (`pages/food.ts` and its views, #119, mockups 02–06 and 16): the Food page (`/pizza/`: open orders, today's earlier ones, a stale one to cancel; guests see what the screens show, people not in the event the way to join, ordering off the organiser's note), `/pizza/go` (the screens' QR: the only open order's menu, else the list, L6), starting an order, an order's page (my pizzas, the steps as they happen, where to collect it, "I've got mine") and its menu (filter, prices, own pizza, Other, the same again, edit). Guests reach the Food page and an order's page; the menu needs sign-in. `static/food.js` follows the live stream and redraws the page from its own answer, says "Reconnecting…" while the stream is gone, and filters the menu as you type.
- **The live stream** (`live.ts`, `GET /api/pizza/stream`): every container reads pizza's own event streams off the bus and tells the pages open on it which order changed (id, state, revision; never who or what). A page reads itself again on a change and after a reconnect.
- **Notify's `food` topic** (`topic.ts`): registered at every start, exactly the contract's block in notify.md; Notify turns the events into the last call, "Called in", "Pizza is here", cancellations, a pizza changed by someone else, reminders and the nudge.
- **Money notices** (`notices.ts`, #703): "your share is ready" (the scheduler's `share` step, 5 min after the last money change), "your share changed" (amounts, or whom or how to pay), "marked paid" and the one payment reminder (the `unpaid` step, noon after the order's event day); to the people in the order, never its payer, and never with an amount or the payer's details, which each person reads on their order.
- **The pages** (`pages/`, `static/`): the holder's (`/pizza/hold/{order}`: checklist, call mode, called in, it's here, hand-out) in the hub's look with the event's theme, and the crew's (`/pizza/crew`: the day's orders and one order to step in on; `/pizza/crew/pizzerias`: pizzerias, menus and the menu CSV's preview; `/pizza/crew/settings`: Food settings, saved through admin's settings API as the person). Every page reads and writes through the API itself (`kit.ts`, `viaApi`), so its rights, idempotency and audit are the API's. English and Finnish (`messages.ts`, `messages-fi.ts`) by admin's `language`; `static/pizza.js` adds what is nicer with a script (tick-as-you-read, copy, the 10 s undo of "Everyone got theirs"), and every page works without it.
- **The money pages** (#644, mockups 09, 12, 17 C, 18, 19, 20): the holder's money step (`pages/money.ts`, `money-views.ts`, `receipt-views.ts`: the total on the amount pad, a receipt's photo, the read to check, exact or even, who is paid, "Pay me with", who owes you), amounts and the Paid column on the hand-out, each person's share on My order, the daily record and the export (`pages/record-pages.ts`, `record-views.ts`), Food settings' settling up and AI reader, reading a menu photo (`pages/menu-read.ts`) and Admin → Integrations (`pages/integrations.ts`, `/pizza/integrations`). Forms with photos are multipart (`pages/uploads.ts`) and go on to the API as its image body. `static/money.js` adds the pad's keys, Copy and "Reading the receipt…".

## Environment

`CANCCU_DATABASE_URL`, `CANCCU_MIGRATE_DATABASE_URL` (the migration role), `CANCCU_TENANTS_URL`, plus the kit's `CANCCU_MODULE`, `CANCCU_VERSION`, `CANCCU_VALKEY_URL`, `CANCCU_ADMIN_URL`, `CANCCU_SERVICE_KEY`. Optional: `CANCCU_SECRETS_KEY` and `CANCCU_SECRETS_KEYS_RETIRED` (the kit's secrets key, which seals the AI reader's provider key; without it no key can be set and the reader stays off; the Compose placeholder only with version `dev`), `CANCCU_PIZZA_READER=fake` (CI's fake reader, only with version `dev`), `CANCCU_NOTIFY_URL` (default `http://notify:8080`, where the `food` topic is registered), `CANCCU_SIGNIN_HOSTNAME`, `CANCCU_SUPERADMIN_HOSTNAME`, `CANCCU_IP_MODE=demo` (only with version `dev`).

Through Caddy: `/api/pizza/health`, the contract's `/api/pizza/…` paths, and the pages under `/pizza/`. The shared files volume is mounted at `/files` (receipts).

## Check

```sh
npm ci && npm run lint && npm run typecheck && npm test
```

The tests need a real Postgres, because RLS cannot be faked; without `CANCCU_DATABASE_URL` they are skipped. They drop and recreate the module's tables, so they refuse a database whose name does not end in `_test` ([docs/ci.md](../../docs/ci.md#modules)). The ported legacy tests are the spec: `orders.test.ts` and `cancel.test.ts` (`pizza-orders`), `items.test.ts` (`pizza-routes`), `system.test.ts` (`pizza-db`), `validate.test.ts`, `summary.test.ts` (`pizza-summary`, `pizza-menu-filter`) and `record.test.ts` (`pizza-report`). `test/*.browser.test.ts` drive the attendee's, the holder's and the crew's flows in Chromium (skipped where none starts, required in CI). `ci/stack-smoke.sh` checks the module on the running stack; `scripts/demo-screenshots-pizza.mjs` takes the pages' CI screenshots.
