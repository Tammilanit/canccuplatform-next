# bot

The bot module serves [contracts/bot.md](../../contracts/bot.md): the Discord side of the platform, one module with a pool of Discord clients. Plan and split: [docs/plans/issue-121.md](../../docs/plans/issue-121.md), six links. Link 1 (#760) builds the module on the stack, the fake Discord, the REST and gateway clients, the pool with its lease, `GET /api/bot/connection` (the shared bot) and health. Own applications' writes, binding a guild, routing by guild, clone and the deletion hooks follow in link 2; commands in link 3; rights from roles in link 4; setup in link 5; the Discord page in link 6.

## How it works
- **One container, API and gateway** (O2 of the step 6 plan): `main.py` serves the API and runs the pool in the same process.
- **A thin client of our own** (B2), not discord.py: the contract needs a queue per event inside one client, a cap per queue, an invalid-request breaker that stops instead of retrying, and feeds dropped before anything is stored. `client.py` joins one application's REST side and its gateway shards into the one status the contract shows (`connecting`, `ready`, `rate_limited`, `paused`, `failed`, with `error_code`).
- **REST** (`rest.py`): every call names its event (`tenant`), or none for the platform's own. Each event has its own queue, served in turn, with one job in flight per event, so a burst of one event (a mass of DMs) waits in its own queue and holds one worker at most. A queue holds at most 500 jobs; more is 429 `rate_limited` for that event only. Discord's buckets (route plus major parameter, learned from the `X-RateLimit-*` headers) are waited for, one request in flight per bucket, so the count read before a request is the one Discord last sent. A 429 is waited out and sent again, at most three tries; a global 429 shows as `rate_limited` while it lasts. A 401 stops the client (`failed`, `token_invalid`) until it gets new credentials; 100 invalid answers (401, 403, and 429 but those of a limit shared with other bots) within 10 minutes pause it (`paused`, `invalid_requests`) for 10 minutes, so the VM's address is never blocked for every client on it. A 5xx is `discord_unavailable` and is not retried here; the caller decides.
- **Gateway** (`gateway.py`, `transport.py`): identify, or resume a session after a drop; heartbeats, with the first after a random part of the interval, and a connection whose heartbeat goes unacknowledged closed (4000) and resumed; Reconnect and Invalid Session; the close codes (4004 `token_invalid` stops for good; 4007 and 4009 identify anew; 4010 to 4013 fail). It reconnects by itself, waiting 1 s, then 2, 4 … at most 5 minutes, starting at 1 s again after each READY or RESUMED; a failed attempt shows as `connecting` with `discord_unavailable`. An application whose privileged intents are off in its portal (4014) connects without them and reports `intents_missing` (contracts/bot.md, Missing intents). Shards follow `GET /gateway/bot`, `max_concurrency` per 5 s. A handler's error is logged and never stops the client. Link 1 asks for the `GUILDS` intent only and stores nothing a gateway event carries: the feeds, their intents and their flags come with routing by guild (link 2).
- **The pool and its lease** (`pool.py`, `lease.py`): every 10 s each container reads which applications should run (the shared one from the environment, own ones from `bot_application_routes` and each event's sealed token), renews the leases it holds, takes free ones and closes what it lost or no longer wants. The lease is `bot:lease:<application id>` in Valkey, 30 s, set only if free and renewed or released only by its holder (a check and change in one step on the server). So a client runs in exactly one container; a dead container's clients move to another after 30 s, and a stopped one hands them over at once. An own client opens and closes within a tick of its connection changing, and a rotated token opens a new client: no restart.
- **Status** (`status.py`): the holder writes each client's status and its bot user to `bot:status:<application id>` (60 s, refreshed every tick), so every container answers `GET /api/bot/connection` and health for clients another one holds. A status nobody refreshes runs out and reads as `connecting`. `bot.client.changed` goes to each event the client serves (an own application's event; for the shared client, every event whose guild it serves), at most once a minute per event, the last status winning.
- **Connection** (`connection.py`): `GET /api/bot/connection`, right `bot.connection.read`, on the event's hostname, under the event's admin-access rule. An event with no connection row is on the shared bot at revision 0. Credentials show only whether they are set; their values never leave the database. With no shared application configured, a shared-mode event gets 503 `discord_not_configured`.
- **Health** (`checks.py`): `checks.discord_shared` is `ok` while the shared client is ready, otherwise `degraded` with what it is (`not configured`, `connecting`, `failed: token_invalid` …); `checks.discord_own` counts failing own clients without naming an event and is always `ok`. Neither check is essential, so Discord alone never makes the module `down`, and an own client never even `degraded`.
- **Tables** (`migrations/001_bot.sql`): `bot_connections` and `bot_bindings`, per tenant under RLS, one row per event; the global `bot_guild_routes` (guild → event and application, one per guild) and `bot_application_routes` (own application → event, one each way), on the kit's allow-list (`scripts/tenancy-global-tables.txt`). Own credentials are sealed with the kit's `SecretBox`, bound to the row with the aad `bot:token:<tenant>:<application id>` and `bot:secret:…`; a token that does not open is logged and its client stays closed.

## The fake Discord
`canccu_kit.testing.discord` ([packages/kit-py](../../packages/kit-py/README.md#the-fake-discord)) is Discord for the tests: REST and gateway in-process for the unit tests (`tests/fakes.py` adapts its connection), and the same code as the `fake-discord` container of `deploy/compose.ci.yml`, which the CI stack's bot connects to. Never a real guild, token or id.

## Environment
`CANCCU_DATABASE_URL`, `CANCCU_TENANTS_URL`, `CANCCU_SECRETS_KEY` (and `CANCCU_SECRETS_KEYS_RETIRED`), plus the kit's `CANCCU_MODULE`, `CANCCU_VERSION`, `CANCCU_VALKEY_URL`, `CANCCU_ADMIN_URL`, `CANCCU_SERVICE_KEY`.

The shared bot: `CANCCU_BOT_APPLICATION_ID`, `CANCCU_BOT_TOKEN` and `CANCCU_BOT_CLIENT_SECRET`, all three or none (a part of them stops the start). Without them the module serves, its health says `not configured`, and only events that bring their own application have a bot. Never in the database, never in the repo (`deploy/.env` only).

Optional: `CANCCU_DISCORD_API_URL` (default `https://discord.com/api/v10`; the CI stack points it at the fake), `CANCCU_MIGRATE_DATABASE_URL`, `CANCCU_SIGNIN_HOSTNAME`, `CANCCU_SUPERADMIN_HOSTNAME`, `CANCCU_IP_MODE=demo` (only with version `dev`), `CANCCU_TRUSTED_PROXIES`.

Through Caddy: `/api/bot/health` and the contract's `/api/bot/…` paths.

## Check
```sh
pip install -e ".[dev]" && ruff check . && ruff format --check . && mypy . && pytest
```
The tests of the connection read and the route tables need a real Postgres, because RLS cannot be faked; without `CANCCU_DATABASE_URL` they are skipped, and they refuse a database whose name does not end in `_test` ([docs/ci.md](../../docs/ci.md#modules)). The lease's own tests need a real Valkey (`CANCCU_VALKEY_URL`). Everything else runs against the fake Discord in-process, and one test opens it over a real websocket. CI runs them in the `module (bot)` job; `ci/stack-smoke.sh` checks the module on the stack, and `scripts/demo-stack-test` that the shared client is ready on the fake Discord.
