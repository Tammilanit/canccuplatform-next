## How it works
- **One container, API and gateway** (O2 of the step 6 plan): `main.py` serves the API and runs the pool in the same process.
- **A thin client of our own** (B2), not discord.py: the contract needs a queue per event inside one client, a cap per queue, an invalid-request breaker that stops instead of retrying, and feeds dropped before anything is stored. `client.py` joins one application's REST side and its gateway shards into the one status the contract shows (`connecting`, `ready`, `rate_limited`, `paused`, `failed`, with `error_code`).
- **REST** (`rest.py`): every call names its event (`tenant`), or none for the platform's own. Each event has its own queue, served in turn, with one job in flight per event, so a burst of one event (a mass of DMs) waits in its own queue and holds one worker at most. A queue holds at most 500 jobs; more is 429 `rate_limited` for that event only. Discord's buckets (route plus major parameter, learned from the `X-RateLimit-*` headers) are waited for, one request in flight per bucket, so the count read before a request is the one Discord last sent. A 429 is waited out and sent again, at most three tries; a global 429 shows as `rate_limited` while it lasts. A 401 stops the client (`failed`, `token_invalid`) until it gets new credentials; 100 invalid answers (401, 403, and 429 but those of a limit shared with other bots) within 10 minutes pause it (`paused`, `invalid_requests`) for 10 minutes, so the VM's address is never blocked for every client on it. A 5xx is `discord_unavailable` and is not retried here; the caller decides.
- **Gateway** (`gateway.py`, `transport.py`): identify, or resume a session after a drop; heartbeats, with the first after a random part of the interval, and a connection whose heartbeat goes unacknowledged closed (4000) and resumed; Reconnect and Invalid Session; the close codes (4004 `token_invalid` stops for good; 4007 and 4009 identify anew; 4010 to 4013 fail). It reconnects by itself, waiting 1 s, then 2, 4 … at most 5 minutes, starting at 1 s again after each READY or RESUMED; a failed attempt shows as `connecting` with `discord_unavailable`. An application whose privileged intents are off in its portal (4014) connects without them and reports `intents_missing` (contracts/bot.md, Missing intents). Shards follow `GET /gateway/bot`, `max_concurrency` per 5 s. A handler's error is logged and never stops the client. The client stores nothing a gateway event carries: the router below hands each event on, or drops it.
- **The pool and its lease** (`pool.py`, `lease.py`): every 10 s each container reads which applications should run (the shared one from the environment, own ones from `bot_application_routes` and each event's sealed token), renews the leases it holds, takes free ones and closes what it lost or no longer wants. The lease is `bot:lease:<application id>` in Valkey, 30 s, set only if free and renewed or released only by its holder (a check and change in one step on the server). So a client runs in exactly one container; a dead container's clients move to another after 30 s, and a stopped one hands them over at once. An own client opens and closes within a tick of its connection changing, and a rotated token opens a new client: no restart.
- **Status** (`status.py`): the holder writes each client's status and its bot user to `bot:status:<application id>` (60 s, refreshed every tick), so every container answers `GET /api/bot/connection` and health for clients another one holds. A status nobody refreshes runs out and reads as `connecting`. `bot.client.changed` goes to each event the client serves (an own application's event; for the shared client, every event whose guild it serves), at most once a minute per event, the last status winning.
- **Connection** (`connection.py`): `GET /api/bot/connection`, right `bot.connection.read`, on the event's hostname, under the event's admin-access rule. An event with no connection row is on the shared bot at revision 0. Credentials show only whether they are set; their values never leave the database. With no shared application configured, a shared-mode event gets 503 `discord_not_configured`.
- **Health** (`checks.py`): `checks.discord_shared` is `ok` while the shared client is ready, otherwise `degraded` with what it is (`not configured`, `connecting`, `failed: token_invalid` …); `checks.discord_own` counts failing own clients without naming an event and is always `ok`. Neither check is essential, so Discord alone never makes the module `down`, and an own client never even `degraded`.
- **Writing the connection** (`credentials.py`): `PUT` and `DELETE /api/bot/connection`, the event-admin role itself. An own application's token must open `GET /oauth2/applications/@me` as that application and its secret must get a client-credentials token (`discord_api.py`), both before anything is stored; the transaction then checks the revision again. A rotation brings only the credential that changes. Going back to shared erases both and the application route, and leaves no user on the row. Audited (which credential, never a value), `bot.connection.changed` through the outbox.
- **Binding** (`bind.py`, `bind_page.py`): the start keeps a random `state` in Valkey for 10 minutes (only its SHA-256 is the key) with the event, the caller, the application and the connection's revision. The callback takes it once, exchanges the code, takes the guild from Discord's answer, checks the Discord user against the caller's, Manage Server in the person's own guild list and the bot in the guild, then binds in one transaction that checks the connection and the binding again under the two unique keys. The browser goes to `/bot/?bind=…` on the event's primary hostname, or gets a result page on the sign-in host (styled with admin's `ui.css`, never framed, no referrer).
- **Ending a binding** (`guild.py`): one path for the event admin's `DELETE /api/bot/guild`, the superadmin's `POST /api/bot/guilds/{guild_id}/unbind` (superadmin hostname only, admin's `superadmin` flag), `bot_removed` and a deleted event: the binding and its route go in one transaction, then the guild loses the event's commands and the shared bot leaves it. `POST /api/bot/guild/commands/sync` writes the commands again in the background.
- **Commands** (`commands.py`): the guild gets exactly the commands of the event's enabled flags in one bulk overwrite, none for an archived event, on bind, on `tenants.flags.changed`, on archiving and on sync; a failure shows on the binding (`failed`, `rate_limited` or `missing_access`). A set is written only when its hash differs from the one last written to that guild (`bot_bindings.commands_hash`, O4), except on the admin's sync; a failed write forgets the hash. `COMMANDS` holds the event's commands (below); the Finals track adds `/finals`. At start every bound guild's set is written again (`register_all`), the hash keeping an unchanged one from costing a write.
- **The command framework** (`framework.py`, `interactions.py`; contracts/bot.md, The command framework): a command declares its name, flag, descriptions in English and Finnish (`texts.py`), options or subcommands, its buttons' and forms' handler and its error codes in words. The framework defers it at once, runs each interaction as its own task (a slow command never holds the next one on the shard), gives the handler 10 seconds (then "did not answer in time. Nothing was sent"), checks the flag again, and turns `NeedsSignIn`, `NoRight`, `Refused` and `Unreachable` into private sentences: the sign-in reply has a Sign in button to `/admin/sign-in` on the event's hostname. Answers are private, in the person's Discord language when the platform speaks it, with the event's colour on embeds. A link that comes with a provider's `expires_at` is edited to "run the command again" when it runs out; that timer lives in the container that answered, and a restart before it fires leaves the link as it was until Discord's 15 minutes end. A command with no flag is on wherever the event has a guild; a message command (`menu`, with a short `key` for its components) gets the message as `Context.target` (`payloads.py` reads what Discord sends); a command whose first step is a form (`form`) answers with it at once; subcommands may sit in a group (`/ticker schedule add`). What a step keeps for the next (a draft, the photo a message became) waits in Valkey per event (`notes.py`, `bot:note:<tenant>:<kind>:<key>`), and an upload goes to a module as a multipart form (`Upload`). `tests/trial.py` is the test command shaped like `/finals`.
- **The commands** (contracts/bot.md, Commands; mockups 07 to 09 of the step 6 brief): the attendees' doors `/food` (flag `pizza.enabled`), `/now`, `/hub` and `/privacy` (`doors.py`), each read as the person and answered with a link button to its page; `/announce` (`announce.py`): a form at once, a preview from Moments with the level as buttons, Send through Moments' API (all four channels, now, every zone) and "Open the composer" for the rest; `/ticker` (`ticker.py`, `days.py` for "Sat and Sun", `clock.py` for `HH:MM` in the event's zone) on Screen's ticker and its weekly windows; "Send to the screen" and "Remove from the screen" (`photos.py`, flag `screen.photos`): a message's first picture, fetched only from Discord's file hosts (`attachments.py`), to Screen's photo wall with the message id as `source_ref` and no name. Rights are the modules' own, through the acting token; texts in English and Finnish beside each command. Every reply that quotes someone's words strips links off the event's hosts.
- **The announcement post** (`posts.py`, `migrations/006_posts.sql`; contracts/bot.md, The announcement post): on Moments' `moments.announcement.sent` with the Discord channel, one embed in the `announcements` purpose, edited on `.changed` and marked withdrawn on `.withdrawn`; an urgent one pings the setting `announce_role` (admin's `declarations/bot.yaml`, read with the kit's `SettingsClient`), never `@everyone`. Every container reads Moments' streams, so the row in `bot_posts` is claimed before the post goes out and only one container posts; a post Discord cannot take now is released and raised, so the bus runs it again. The posts go with the binding (unbind, clone, deleted event). Posts are in English for now.
- **Components** (`components.py`): a button, a Yes or No and a form carry their command, step and arguments in a custom id signed for the event with a key derived from the service key, dated and refused after 15 minutes, so they keep no state in the container and work after a restart.
- **Acting as the person** (`acting.py`): a command's call to a module asks admin for an acting token (the bot's service identity and `CANCCU_BOT_ADMIN_KEY`), then calls the module on its event's hostname with the token, the bot's service identity for that module and the interaction id as `Idempotency-Key`. A module is at `CANCCU_<MODULE>_URL`, else `http://<module>:8080`. Without an account or membership the person gets the sign-in reply; without the right, which right.
- **Providers** (`providers.py`): a call to an outside provider sends the event's bearer secret for it, when it has one: `PUT`/`DELETE /api/bot/providers/{provider}/secret`, the event-admin role, sealed with the aad `bot:provider:<tenant>:<provider>` (`migrations/003_commands.sql`), write-only and audited without the value.
- **The guard** (`guard.py`, port of the legacy `tourney_guard`): every body the bot sends pings nobody (`allowed_mentions` empty), or only an urgent announcement's picked role; `strip_foreign_links` keeps only links to the event's hosts in text built from other people's words.
- **The event's voice** (`look.py`): the bot's nickname in the server is the event's name, from `GET /api/tenants/current` on the event's hostname, set after a bind and on `tenants.tenant.changed` with `name`; embeds take theming's `embed_color` (`GET /internal/theming/current`). Both kept a minute per event.
- **Purposes** (`purposes.py`, `templates.py`, `server.py`; contracts/bot.md, Purposes): the fixed catalogue, each purpose under its feature's flag with its template, and the channel or role id the event picked (`migrations/004_purposes.sql`). Every state and pick list is read live from Discord (`server.py`: the guild's channels and roles and the bot's own roles), outside the event's client queue like the command writes, so a channel deleted in Discord shows `missing` on the next read (E3). Create what is missing makes roles first, then channels with overwrites cut to what the bot holds (Discord refuses more), and no role while a bound role sits at or above the bot's (E6). The purposes go with the binding: an unbind forgets them, a clone moves them.
- **The setup check** (`setup_check.py`, `perms.py`; contracts/bot.md, The setup check): per feature that is on, the purpose's channel, the bot's permissions in it (computed as Discord does), the application's intents (its flags on Discord) and the role order, each with a whole-sentence fix. The last result is kept in Valkey a week per event and guild (`bot:check:<tenant>:<guild>`); `POST` runs it again. `allow_in_channel` fixes give the bot, in its own overwrite, what a channel took from its role. `tournament.enabled` is not declared yet (step 7), so Tournaments and Match voice read `not_on` everywhere.
- **Routing** (`router.py`): each client asks for guilds, members and presences (privileged), voice states and guild messages, never message content. A gateway event reaches its event only through a guild route for the client's own application, an event that is not archived and, for a feed, its flag (`bot.presence`, `bot.members`, `bot.voice`, `bot.messages`) on; everything else is dropped before a handler. The guild's snapshot (`GUILD_CREATE`) and a members chunk (the answer to op 8) reach the counts with each feed's part (members, presences, voice states) dropped the same way, and the channel and @everyone role changes with them. The bots a snapshot, a chunk or a dropped member or voice event names go on alone (`BOTS_SEEN`), whatever the flags, so no count takes a bot in. Routes and events' flags are read from memory for at most 10 s. An interaction in an unbound guild, a DM to the shared bot and one of an archived event get a short private answer; an own bot's DM goes to its event. The shared bot leaves a guild no event chose after 15 minutes (checked again then); a guild that removes the bot ends its binding (`bot_removed`), one that is only unavailable stays bound.
- **Counts** (contracts/bot.md, Counts; `feeds.py`, `live.py`, `counts.py`): each client's routers hand the feeds' events and the guild's snapshot and channel changes to one `Feeds` per client, which keeps each event's live state (`live.py`: members, bots, statuses, activities, voice channels and which channels everyone can see, by Discord id only) in memory and writes it behind to Valkey every 5 s, so a restart reads it back; a delta counts as written only once Valkey took it. Each write and each minute first read the guild routes and the event fresh, and an event the client no longer serves (archived, deleted, unbound or moved) has its live state dropped, never written, also at the client's close. A guild bound after its snapshot (every bind: `bind.py` needs the bot in the guild first) gets its channels and roles over REST at the next minute (once its snapshot showed the bot is in it: `Router.guilds`, so Discord is never asked what it would refuse) and, as does a guild whose members or presence feed came on since, its members and presences through op 8 (`DiscordClient.request_members`, only with the members intent); a large guild asks for its members after its snapshot, so its offline bots are known. No minute is written for a guild nothing is known of yet. The trackers are ports of the legacy canccubot's: `presence_tracker.py` (members by status, bots skipped from a bot set apart from the members feed, Discord's member count for a large guild's offline members), `activity_tracker.py` (the `game_detector`'s count of "playing" activities), `voice_tracker.py` (people in voice; rooms named only when public) and `message_tracker.py` with `channels.py` (chat activity in the channels everyone can read; the legacy's per-person counts are dropped, D6). Once a minute (`Feeds.tick`, in the container holding the client's lease) the minute goes to `bot_counts_minute` with `bot.presence.counted`, `bot.activities.counted` and `bot.voice.counted` through the outbox; an hour that ended is folded into `bot_counts_hour` and `bot_activity_hour` (player-minutes) with `bot.messages.counted`. A minute or an hour is written once (its key), so a handover or a second tick counts nothing twice. A message is counted in Valkey when it comes (`bot:count:<tenant>:messages:<minute>`, 2 hours), so a minute the bot missed keeps its messages. The live state goes at archiving (`lifecycle.py`), at an unbind or a move (the next minute), and a feed's part when its flag goes off; the counts stay with the event until it is deleted. `stats.py` serves `GET /api/bot/stats` to members, and to guests as the info-page mode allows (`access.is_member` is the membership seam, as agenda's). **The module paths for the screens** (`presence_paths.py`, #851; contracts/bot.md, For the screens): `GET /internal/bot/presence/playing` and `/voice`, for the screen module's service identity only (`app.py` serves `/internal/` outside tenant resolution, behind the kit's `ServiceIdentityMiddleware`), answer from the live state read back from Valkey, so any container answers: players per game of the catalogue (a person once per game; a hidden game's activities nowhere; the rest one unmatched entry, never named) and people per public voice room, without bots and `hidden_discord_ids`. `as_of` is the holder's last write behind (`bot:live:<tenant>:as_of`); `available: false` with no binding, a client not `ready` or `rate_limited` on the status board, the feed's flag off or the event archived.
- **Clone** (`clone.py`): `POST /api/bot/clone` moves the source's own application (sealed again for the new event) and binding, with both routes, in one transaction that switches the tenant setting between the two events; the source falls back to shared. The running client follows the rewritten routes, so it serves the new event without a restart.
- **Lifecycle** (`lifecycle.py`): `tenants.tenant.deleted` deletes the event's rows, routes and outbox and the shared bot leaves its guild; `tenants.user.deleted` drops the user from `bound_by` and `updated_by` in every event a route names (only rows with a route name a user); a status or flags change reaches the routers at once and re-registers the commands.
- **Seams** (`access.py`, `config.py`; docs/plans/issue-121.md, B11): `is_event_admin` (the event-admin role is "holds `admin.rights.write`" until #150, so only the owner writes); `Hosts.callback_origin` (the install callback on `CANCCU_SIGNIN_HOSTNAME`, else on `CANCCU_PUBLIC_URL`, admin's public origin); `UsersReader` (a user's Discord id from tenants, 404 until #150, so a bind fails closed with `discord_user_mismatch`); `SeriesReader` (the caller an event admin of both events of one series, from tenants' series read, 404 until #150, so a clone fails closed with 403); the deletion events are handled as delivered until #150 emits them. `hidden_discord_ids` (`privacy.py`, D3 of docs/plans/issue-122.md): the Discord ids every count leaves out (members with `presence_opt_out`), the empty set until #150 serves the flag; #122's link 2b replaces it with admin's read of people by Discord id, and no output names anyone until then. `games_catalogue` (`catalogue.py`): the event's games for the stats' top games, the empty catalogue until the Games track's module serves it, so the top games list stays empty until then. Membership for a command (who gets the sign-in reply) is admin's seam (`modules/admin/src/canccu_admin/acting.py`): someone who signed in and was not removed.
- **Tables** (`migrations/001_bot.sql`, `002_outbox.sql`, `004_purposes.sql`, `005_counts.sql`, `006_posts.sql`): `bot_connections` and `bot_bindings`, per tenant under RLS, one row per event; `bot_purposes`, per tenant, one row per picked purpose; `bot_posts` (`006_posts.sql`), per tenant, the announcement posts' message ids; `bot_counts_minute`, `bot_counts_hour` and `bot_activity_hour` (`migrations/005_counts.sql`), per tenant, counts only; the global `bot_guild_routes` (guild → event and application, one per guild) and `bot_application_routes` (own application → event, one each way); the kit's outbox (`bot_outbox`, per tenant, and the global `bot_outbox_tenants`). The global ones are on the kit's allow-list (`scripts/tenancy-global-tables.txt`). Own credentials are sealed with the kit's `SecretBox`, bound to the row with the aad `bot:token:<tenant>:<application id>` and `bot:secret:…`; a token that does not open is logged and its client stays closed.

## The fake Discord
`canccu_kit.testing.discord` ([packages/kit-py](../../packages/kit-py/README.md#the-fake-discord)) is Discord for the tests: REST and gateway in-process for the unit tests (`tests/fakes.py` adapts its connection), and the same code as the `fake-discord` container of `deploy/compose.ci.yml`, which the CI stack's bot connects to. Never a real guild, token or id.

## Environment
`CANCCU_DATABASE_URL`, `CANCCU_TENANTS_URL`, `CANCCU_SECRETS_KEY` (and `CANCCU_SECRETS_KEYS_RETIRED`), `CANCCU_BOT_ADMIN_KEY` (the acting token's second key, held by admin and the bot only; without it no command acts for anyone), plus the kit's `CANCCU_MODULE`, `CANCCU_VERSION`, `CANCCU_VALKEY_URL`, `CANCCU_ADMIN_URL`, `CANCCU_SERVICE_KEY`.

The shared bot: `CANCCU_BOT_APPLICATION_ID`, `CANCCU_BOT_TOKEN` and `CANCCU_BOT_CLIENT_SECRET`, all three or none (a part of them stops the start). Without them the module serves, its health says `not configured`, and only events that bring their own application have a bot. Never in the database, never in the repo (`deploy/.env` only).

Optional: `CANCCU_<MODULE>_URL` (a module a command calls, and `CANCCU_THEMING_URL` for the colour; default `http://<module>:8080`), `CANCCU_PUBLIC_URL` (the bind's callback origin without a sign-in host), `CANCCU_DISCORD_API_URL` (default `https://discord.com/api/v10`; the CI stack points it at the fake), `CANCCU_MIGRATE_DATABASE_URL`, `CANCCU_SIGNIN_HOSTNAME`, `CANCCU_SUPERADMIN_HOSTNAME`, `CANCCU_IP_MODE=demo` (only with version `dev`), `CANCCU_TRUSTED_PROXIES`.

Through Caddy: `/api/bot/health` and the contract's `/api/bot/…` paths.

## Check
```sh
pip install -e ".[dev]" && ruff check . && ruff format --check . && mypy . && pytest
```
The tests of the connection read and the route tables need a real Postgres, because RLS cannot be faked; without `CANCCU_DATABASE_URL` they are skipped, and they refuse a database whose name does not end in `_test` ([docs/ci.md](../../docs/ci.md#modules)). The lease's and the live state's Valkey tests need a real Valkey (`CANCCU_VALKEY_URL`). `tests/test_soak.py` runs 2,000 members and 5,000 presence updates through the in-process fake gateway (O1). Everything else runs against the fake Discord in-process, and one test opens it over a real websocket. CI runs them in the `module (bot)` job; `ci/stack-smoke.sh` checks the module on the stack, and `scripts/demo-stack-test` that the shared client is ready on the fake Discord.
