# notify

The notify module serves [contracts/notify.md](../../contracts/notify.md): topics, notifications to attendees' phones and the inbox. Plan and split: [docs/plans/issue-188.md](../../docs/plans/issue-188.md). Package 1 (#188) built the topic registry, each event's topic configuration, the trigger engine that turns domain events into notifications, and the inbox; #228 adds custom topics and the notification pages, #227 check-in codes and the check-in page, and #225 Web Push, subscriptions and the push delivery rules. Quiet hours, Discord DMs, follows and privacy follow in #226.

## How it works
- **Tenancy:** each request's event comes from its `Host`, through the kit's `TenancyMiddleware` and `TenantResolver` (`CANCCU_TENANTS_URL`). The registry (`notify_topic_types`) and its history are global, as the contract says; everything else is per tenant under RLS. Requests run as `canccu_notify_app` (`SET LOCAL ROLE` inside each transaction).
- **Registry:** modules register their topic types with `PUT /internal/notify/topic-types/{topic}`, signed with the kit's module identity. A module registers only its own topics (the signed caller must be the `owner`) and only its own events. Every change is appended to `notify_topic_type_history`, which the app role may insert into and read but never change.
- **Configuration:** `PUT …/config` is versioned by the write itself (two writes of one `config_version` cannot both succeed), refused on an archived event (409 `event_archived`) and while admin is unreachable, and audited through the tenants module inside its transaction: a change whose audit entry cannot be written is rolled back. `enabled` and the `schedule` topic's `lead_minutes` live only in admin's settings `topics` and `schedule_lead_minutes` (#251): a config write carries them there with the kit's `SettingsClient.write` (`PATCH /internal/admin/settings/notify`) inside its transaction, so admin refusing it rolls the config write back, and a stale settings version is computed again once from the reloaded settings. A write in admin's settings is therefore seen at once; Notify keeps no copy. An unset `topics` means every topic, so switching one off writes the list of all the others. A new custom topic joins a set `topics` list and a removed one leaves it. Without settings, the type's defaults apply.
- **Custom topics:** `PUT`/`DELETE /api/notify/topic-types/custom_…` (`custom_api.py`). The row keeps only what narrows the base (`based_on`, title, defaults, conditions, `revision`); `custom.derive` builds the registration from the base on every read, so the base's next version reaches it. A new custom topic is switched on, also when admin's setting `topics` lists the topics. Its configuration starts from its base's (parameters) and can only narrow the base's channels. A source event that matches both makes two notifications; `notify_notifications.based_on` lets the inbox show a reader only the custom one (`inbox.collapse`).
- **Pages** (`/notify/admin/topics`, Caddy strips `/notify`; in admin's "Event" menu): server-rendered, phone-first, no script, the stable classes of `packages/ui` and its `ui.css`. The topic list (`topic_pages.py`) shows each topic's configuration as a form for `notify.topics.write`, which sends only the values that changed, and how many notifications each topic made for `notify.stats.read` (counts, never recipients). The custom-topic form (`custom_pages.py`) picks a base first, then offers only the defaults the base has on, and conditions as rows; conditions it cannot show (`nearest_in`, against a parameter) are kept as set through the API.
- **Trigger engine:** `engine.py` is pure (an envelope and a registration in, candidates out). `consumer.py` reads every module's tenant stream, skips events no registered trigger listens for, checks each enabled topic's triggers, takes the dedupe key only when a notification is made, and writes one notification for event-wide parts or one per recipient for personal parts. Entity-scoped parts make nothing until follows exist (#226).
- **Time zones:** templates format `|time` and `|date` in the event's time zone. The stream consumer has no request, so each request stores the event's zone from its tenant context in `notify_event_state`; an event that no request has reached yet formats in UTC.
- **Members:** until the tenants membership API lands (#150), every valid session on the event's hostname counts as a member (`access.is_member`), as in the agenda.
- **Inbox:** `GET /api/notify/inbox` with a session, or with a subscription's token (`Authorization: Bearer`), which reads its owner's event-wide audience but never their personal notifications.
- **Web Push:** `webpush.py` is VAPID (RFC 8292) and `aes128gcm` (RFC 8291) on `cryptography`, tested against RFC 8291's own example; `push.py` sends (no redirects, `Urgency`, `TTL` to the notification's `expires_at`). The payload is only `{"v", "id", "topic", "urgent"}`.
- **Subscriptions:** the endpoint is stored in clear (it is the replace key) and must be an https URL of a DNS name on port 443, never an address (also not one written as numbers such as `127.1`) or a local name, because Notify POSTs to it. The browser's `p256dh` and `auth` are sealed with the kit's `SecretBox` (bound to the event and the subscription); the token is kept only as its SHA-256.
- **Delivery:** creating a notification also writes one `notify_deliveries` row per phone that may get it (the topic's part switched on in the subscription, `public` for guests, `attendees` for members, the person's channel choice, which is the part's default until #226, and no guests while the info pages are `sign_in`), and sends right after the commit. Sending claims rows with `FOR UPDATE SKIP LOCKED` and takes the cap decision in a short transaction that marks them `sending`, sends with no transaction open, then records each answer; a row that cannot be sent (keys that do not open, a client error) fails alone. A loop in every container sends what is left, including `sending` rows whose 5-minute lease ran out after a crash. Until #226 stores a person's channel choices, a signed-in user gets a push only where the part's push default is on: a phone switch turned on for a part whose default is off shows as on but pushes nothing. The hourly cap (`hourly_cap`, default 6) counts notifications per recipient (the user, or the subscription for a guest) over the last 60 minutes; urgent ones go over it and count. A capped push stays in the inbox. A recipient whose phone gets a custom topic's push skips its base's push for the same source event, as the inbox collapses them. A push service's 404 or 410 deletes the subscription. Guests' pushes follow the info-page mode and status (none in mode `sign_in` or while the event is a draft) that the last request on the event's hostname saw; each request compares them with the stored row, so every container keeps it current.

- **Check-in (#227):** `checkin.py` serves the rotating codes and check-ins; `checkin_page.py` the page a scanned QR opens (`/notify/check-in`, Caddy strips `/notify`). Each event gets a random 32-byte key on its first code request, stored sealed with the platform secrets key (`CANCCU_SECRETS_KEY`, the kit's `SecretBox`); no code is stored. The opened key is kept per event in the process (`Deps.check_in_keys`): a key never changes, only its seal. A key sealed with a retired secrets key is sealed again with the current one when it is read (#289), so after a rotation every event's key moves as soon as a code is shown or a check-in made, and the retired key can then be dropped from `CANCCU_SECRETS_KEYS_RETIRED`. A key that no longer opens (its secrets key dropped too early) is logged once per container and event, and codes and check-ins there answer 503 `unavailable` until the key is restored. The rotation is the admin setting `check_in_rotation_seconds`; while admin is unreachable, codes answer 503 rather than guess it. A change of the setting voids the code on screen until the screen fetches the next one: periods are counted from the epoch in the new length, so the shown code matches no period any more and a scan of it is refused. A signed-out phone is sent to admin's sign-in with a return path and comes back to the page; checking in takes a tap, never a page load. Every error on the page is a page, never the API's JSON: also those of the kit's middleware (the tenants module unreachable, a refused origin, a hostname that is no event's), through the kit's `error_response` hook. Only the screen module may fetch codes on the internal path (403 `service_forbidden` for any other). Fetching a code follows the event's admin-access rule, and an archived event takes no check-ins and makes no key (409 `event_archived`). The code's `url` is absolute on the event's `primary_hostname`, or a path while the event has none (the IP-mode stack). The internal code path finds its event through `TenantResolver.by_id`. A check-in and its `notify.checkin.recorded` are one transaction: the event goes through the kit's `Outbox` (`notify_outbox`, sent after the commit; a failed send is retried by a loop in every container, every 2 seconds, through the global `notify_outbox_tenants`), so the module named in `purpose` learns of every check-in (#288). Check-in is never mandatory: nothing else in Notify reads check-ins (`tests/test_never_mandatory.py`).

## Environment
`CANCCU_DATABASE_URL`, `CANCCU_TENANTS_URL`, `CANCCU_NOTIFY_VAPID_PRIVATE_KEY` (the platform's VAPID private key, a raw P-256 key in base64url: `python -m canccu_notify vapid-keygen` prints one; without a valid one the module does not start, and a new one breaks every existing push subscription, so it is kept like the secrets key), `CANCCU_SECRETS_KEY` (`<version>:<base64 of 32 bytes>`; it seals the check-in keys and the phones' push keys; deploy/compose.yml has a placeholder that the kit's `SecretBox.from_env` refuses, also as a retired key, unless the version is `dev`), plus the kit's `CANCCU_MODULE`, `CANCCU_VERSION`, `CANCCU_VALKEY_URL`, `CANCCU_ADMIN_URL`, `CANCCU_SERVICE_KEY`. Optional: `CANCCU_PUBLIC_URL` (the VAPID subject; Apple's push service needs one), `CANCCU_SECRETS_KEYS_RETIRED`, `CANCCU_MIGRATE_DATABASE_URL` (the migration role; without it the login role migrates, as in the tests), `CANCCU_SIGNIN_HOSTNAME`, `CANCCU_SUPERADMIN_HOSTNAME`, `CANCCU_IP_MODE=demo` (only with version `dev`), `CANCCU_TRUSTED_PROXIES`.

Through Caddy: `/api/notify/health`, the contract's `/api/notify/…` paths and the pages under `/notify/` (the topic pages and the check-in page; `/notify` and `/notify/` redirect to the topic list, keeping their query). `/internal/notify/…` is never routed, nor `/notify/internal/…`, `/notify/api/…` or `/notify/health`, which Caddy answers 404 before the `/notify/` prefix rule. A signed-out browser on a topic page goes to `/admin/sign-in?next=<this page>` and comes back to it, by the same rules as agenda's pages (the kit's `sign_in_return`), with the topic list where agenda has its list.

## Check
```sh
pip install -e ".[dev]" && ruff check . && ruff format --check . && mypy . && pytest
```
The engine tests run anywhere. Everything else needs a real Postgres, because RLS cannot be faked; without `CANCCU_DATABASE_URL` those tests are skipped. They empty the module's tables, so they refuse a database whose name does not end in `_test` ([docs/ci.md](../../docs/ci.md#modules)). They include the cross-tenant leak tests (`tests/test_leak.py`). CI runs them in the `module (notify)` job ([docs/ci.md](../../docs/ci.md#modules)):
```sh
docker compose -f ../../deploy/compose.yml -f ../../deploy/compose.test.yml up -d --wait postgres
# canccu_test is made once, as in docs/ci.md#modules (Locally)
CANCCU_DATABASE_URL=postgres://canccu:canccu-local-only@127.0.0.1:5432/canccu_test pytest
```
