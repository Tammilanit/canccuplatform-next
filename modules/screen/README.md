# screen

The venue screens ([contracts/screen.md](../../contracts/screen.md)). It holds the module's skeleton, devices with pairing, zones with assignments and mirroring (#220), device heartbeat and health (#222), and playlists, schedule windows, pushes and the tick (#216); moving devices (#221), assets (#217), the ticker and photos (#218) and the player (#109) build on it.

- **Stack:** Node 22, Fastify 5, `pg`, on `@canccu/kit` ([0006](../../docs/decisions/0006-stack.md)). Port 8080. Caddy routes `/api/screen/*` here unchanged and `/api/screen/health` to `/health`.
- **Env:** the kit's (`CANCCU_MODULE`, `CANCCU_VERSION`, `CANCCU_VALKEY_URL`, `CANCCU_ADMIN_URL`, `CANCCU_SERVICE_KEY`), plus `CANCCU_DATABASE_URL` (the login role it serves as), `CANCCU_MIGRATE_DATABASE_URL` (the migration role), `CANCCU_TENANTS_URL`, `CANCCU_SIGNIN_HOSTNAME`, `CANCCU_SUPERADMIN_HOSTNAME` and `CANCCU_IP_MODE`.
- **Data:** `migrations/*.sql`, run at start by the kit's `runMigrations` (ledger `screen_migrations`). `devices` is the one global table (device identity only); every other table (`assignments`, `screen_zones`, `screen_zone_seeds`, `screen_playlists` with `screen_playlist_items`, `screen_schedules`, `screen_pushes`, `screen_zone_playback`, `screen_agenda_items`) is per event under RLS, and requests run as `canccu_screen_app`. Open pairing codes live in Valkey for 10 minutes, device commands for 60 seconds, device health (the last heartbeat, online deadlines and page loads) for up to 7 days; no device token is ever stored, only its SHA-256.
- **Scheduler core** (`src/schedule/`, pure, no routes yet): weekly windows in the event's time zone (`window.ts`), the winner among a zone's weekly and agenda-bound windows (`winner.ts`) and "what would play at…" with the next change (`simulate.ts`). Clock, time zone, the agenda items' times and the playlists' priorities come in as arguments, so the tick and the simulate route (#216) share one rule and the daylight-saving tests pin every input. Ported from the legacy signage `scheduler.ts` and `schedule-window.ts` with their tests; the calendar drag helpers go with Studio (#190).
- **Playback core** (`src/playback/`, pure, no routes yet): a playlist's timeline and frames with their progress-bar timing (`timeline.ts`, `engine.ts`); bookmarks that the tick pauses when a playlist stops and resumes when it plays again, so a deck comes back at its slide and no offset counts twice; a zone's `break` playlists as one state value the tick advances with `stepBreaks` (`breaks.ts`: due times, the daily window, priority chaining, the `break_min_gap_seconds` gap) and what a running break shows (`break-play.ts`: play-once, a looping timeline that goes on where the last break stopped, slideshow dwell with up to 10 s overrun, a shuffle seeded by zone, playlist and start). `projectBreaks` runs that step forward on a copy for simulate's `in_break` and `next_change_at`. Ported from the legacy signage `playback-engine.ts`, `playback-bookmark.ts`, `advt-scheduler.ts`, `advt-window.ts`, `advt-gap-settings.ts` and `advt-playback.ts` with their tests.
- **Content** (`src/content/`): playlists (one document with items, break settings and `revision`), schedule windows (weekly or bound to a run-of-show item, `revision` for conflicts), pushes and simulate, every write audited in its transaction. Bodies are checked in `input.ts` (ported from the legacy `api-schemas.ts` and the length and slide-range rules of `playlist-builder.ts`); the asset-kind rules need the assets (#217). `agenda.ts` keeps `screen_agenda_items` from the `agenda.item.*` events, read from the streams' start at every boot, so bound windows follow delays, crew items included.
- **The tick** (`src/tick/`): every second, in every container, each zone of each event with screens advances once (`advanceZone`: the newest push above the winning window, bookmarks paused around breaks and switches, `stepBreaks`); a Valkey claim per zone and second gives each step to one container, and only a changed state is written to `screen_zone_playback`. It also ends expired pushes (`screen.content.cleared`, `reason: expired`, audited without an actor). Reads, simulate included, never write. Assets come through an `AssetReader`; until #217 supplies one nothing is playable, so breaks are skipped and bookmarks stay at the start.
- **Settings:** declared in `modules/admin/declarations/screen.yaml`, read through the kit's settings client. `offline_after_seconds` counts as at least twice `heartbeat_seconds`, so one late heartbeat never takes a screen offline; while admin is down the defaults hold.
- **Routes so far:** `POST`, `DELETE /api/screen/pairing`, `GET /api/screen/pairing/{pairing_id}`, `GET`, `POST /api/screen/devices`, `PATCH /api/screen/devices/{device_id}`, `POST /api/screen/devices/{device_id}/revoke`, `POST /api/screen/device/heartbeat`, `PUT`, `DELETE /api/screen/devices/{device_id}/assignment`, `POST /api/screen/devices/{device_id}/commands`, `GET`, `POST /api/screen/zones`, `GET`, `PUT`, `DELETE /api/screen/zones/{zone_key}`, `GET`, `POST /api/screen/playlists`, `GET`, `PUT`, `DELETE /api/screen/playlists/{playlist_id}`, `GET`, `POST /api/screen/schedules`, `PUT`, `DELETE /api/screen/schedules/{schedule_id}`, `GET /api/screen/schedules/simulate`, `POST /api/screen/push`, `DELETE /api/screen/push/{push_id}`. `requireDevice` (`src/device-access.ts`) is the check the device routes of later slices run; `takeCommands` (`src/assignments.ts`) is what the push channel (#109) delivers, and `ZONE_USES` (`src/zones.ts`) lists what keeps a zone in use (screens, windows, pushes, break playlists).
- **Health** (`src/health.ts`): every heartbeat moves the device's deadline (the heartbeat plus `offline_after_seconds`) in one Valkey set per event; a sweep in every container, every 5 seconds, takes the passed deadlines and emits `screen.device.offline` once each. `GET /api/screen/devices` shows each device's `health` with the `clock_drift` and `shared_token` flags. `state_lag` waits for the zone's state version, which the composed state (#109) brings.
- **Zones:** an event gets its `main` zone once, on `tenants.tenant.created` or its first zone, assignment or pairing request, whichever comes first; a deleted `main` is not made again. `detachDevice` (`src/detach.ts`) is the one place that clears mirrors and sound devices when a device leaves the event.

- **Cookies** `canccu_pairing` and `canccu_device` are always `Secure`, as the contract says, so browsers keep them only over HTTPS: the IP-mode demo stack (plain http on port 80) cannot pair a real kiosk until TLS (#5). The tests send the cookies themselves.

## Check

```sh
npm ci && npm run lint && npm run typecheck && npm test
```

The tests need a Postgres for RLS and skip without one. Point `CANCCU_TEST_DATABASE_URL` at a throwaway database (the tests drop and recreate the screen tables) as a superuser; requests still run as the app role, which RLS binds:

```sh
docker run -d --rm --name canccu-screen-test -e POSTGRES_PASSWORD=test -p 127.0.0.1:55432:5432 postgres:17.11-alpine
CANCCU_TEST_DATABASE_URL=postgres://postgres:test@127.0.0.1:55432/postgres npm test
docker stop canccu-screen-test
```

CI runs them against its own Postgres in the `module (screen)` job ([docs/ci.md](../../docs/ci.md#modules)).
