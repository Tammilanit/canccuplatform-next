# theming

Each event's theme ([contracts/theming.md](../../contracts/theming.md)). The first slice (`theming-core`, [docs/plans/issue-185.md](../../docs/plans/issue-185.md)) holds the module's skeleton, its store, the current theme and the served theme files; #186 adds embeds in the same-host sandbox; #241 drafts, publish, restore and the history; #242 uploads of images and fonts; #243 the brand kit; #244 packages; #245 CSS and templates; #246 the small-text warning, pins and retention. The pages (#247) build on it.

- **Stack:** Node 22, Fastify 5, `pg`, on `@canccu/kit` and `@canccu/ui` (the token defaults) ([0006](../../docs/decisions/0006-stack.md)). Port 8080. Caddy routes `/api/theming/*` and `/theming/*` here unchanged, and `/api/theming/health` to `/health`.
- **Env:** the kit's (`CANCCU_MODULE`, `CANCCU_VERSION`, `CANCCU_VALKEY_URL`, `CANCCU_ADMIN_URL`, `CANCCU_SERVICE_KEY`; admin also answers the profile's theme), plus `CANCCU_DATABASE_URL` (the login role it serves as), `CANCCU_MIGRATE_DATABASE_URL` (the migration role), `CANCCU_TENANTS_URL`, `CANCCU_SIGNIN_HOSTNAME`, `CANCCU_SUPERADMIN_HOSTNAME` and `CANCCU_IP_MODE`.
- **Data:** `migrations/*.sql`, run at start by the kit's `runMigrations` (ledger `theming_migrations`). Every table is per event under RLS, and requests run as `canccu_theming_app`: `theming_files` (content-addressed, `<sha256>.<ext>` under `/files/<tenant>/theming/files/`), `theming_drafts`, `theming_revisions` (immutable; the highest is current), `theming_file_refs` (what refers to a file: `draft` or `r:<revision>`), `theming_pins`, `theming_embed_files` (an embed's files by owner, embed and path inside its folder; the only thing that refers to stored HTML, JS and JSON) and `theming_package_files` (migration 004: the package's other files by owner and path, each a stored file or, for an upload that failed its checks, the problem that names it; an `embeds/` path only ever a problem, migration 006). `putEmbed` (`src/embeds.ts`) stores an embed for an owner; the package upload calls it, and publish and restore copy an owner's rows. `theming_drafts.updated_by` (migration 003) names who changed the draft last. Migration 005 adds a revision's generated images (`logo_png`, `icon_192`, `icon_512`, `icon_maskable_512`). Migration 006 lets `theming_files` keep font licences (`txt`, `md`): stored, counted and exported, never served. Migration 007 does the same for a template's text (`mustache`), adds to `theming_package_files` what a CSS file or template found at upload (`refs`, the package paths it names; `warnings`), and to `theming_revisions` the parsed `templates`. Migration 008 adds to `theming_package_files` the font sizes a CSS file sets (`font_sizes`), and to `theming_pins` the revision a timed pin restores (`restores_revision`) and the pin event the row holds (`event_time`, `event_id`). The manifest is checked against `contracts/theme.schema.json` itself (`src/schema.ts`), which the image copies to the same relative place. The prefix keeps them apart from other modules' tables in the shared schema.
- **Routes so far:**
  - `GET /api/theming/current`: the highest revision (with its compiled `css_url` and parsed `templates`), or revision 0: the platform defaults with the profile's `theme` over them, read from admin's `GET /internal/admin/profile/theme` and kept per event for a minute or until `admin.profile.loaded` (`src/profile.ts`; while admin cannot answer, the platform defaults). The profile's logo is not read yet; it will go through the upload checks (`src/uploads.ts`) and the quota like any image. Readable by whoever the event's info-page mode lets in; a session is looked up only when guests are kept out, and any valid session counts as a member until #150 (`isMember` in `src/routes.ts`).
  - The draft, to `theming.theme.write` within the admin address rule: `GET`, `POST` (from `current`, `defaults` or a `revision`), `DELETE /api/theming/draft`; `PATCH …/draft/tokens`; `PUT`, `DELETE …/draft/layouts/{id}`. Every change goes through one write path (`editDraft` in `src/drafts.ts`, plan D3): lock the draft, check `draft_version` (409 `version_conflict`), apply the change, re-run every check (`src/checks.ts`: `schema`, `duplicate_id`, `area_outside_grid`, `reference_unknown`, `widget_unknown`, `contrast_low`; `src/manifest.ts`, how the manifest fits the draft's files: `file_missing`, `reference_unknown` for font families and embed files outside their folder, `mode_mismatch`) and store the result with a new version and draft key.
  - The brand kit (`src/brand-routes.ts`): `PUT …/draft/brand` takes `logo` and `icon` (images already stored in the draft, else 400), `primary`, `accent`, `scheme` and `embed_color`, replaces `brand`, `images.logo` and `images.icon` whole, regenerates `tokens.colors` and answers the draft with `adjusted`; it never changes the mode. `POST …/draft/mode` (`mode: simple`, `remove_advanced: true`) removes the CSS, fonts, templates and embeds with their files, the font and size tokens, the layouts' `template` choices and their embed widgets; keeps images, layouts and `motion`; regenerates the colours from `brand` (409 `brand_missing` without it) and answers the removed paths. Removing embeds needs `theming.embeds.write` and is audited (`theming.embeds.removed`). The generation (`src/brand.ts`, plan D5 and D6) takes the scheme's neutral palette (dark is the platform's), shades a given colour that fails in OKLCH lightness only, in fixed steps away from the background, picks `primary_text` as the first of background, white and black that reads on `primary` and on the platform's red, and only when none does, the first that reads on `primary`, with the red shaded for `status_down` until it reads too. The default brand gives the platform defaults exactly; `test/brand.test.ts` pins the output.
  - `PUT`, `DELETE /api/theming/draft/file?path=&draft_version=` for `images/`, `fonts/`, `css/` and `templates/` (`src/file-routes.ts`); embeds and font licences come only with the whole package. The body's bytes decide the type, never the name or `Content-Type`, and the name must agree (`file_type`); a body over 5 MB is 413 `too_large` (`src/uploads.ts`). PNG, JPEG and WebP are decoded and stored re-encoded through `sharp`, metadata dropped, at most 40 megapixels with every frame counted, two decodes at a time (`src/raster.ts`); SVG passes only the rules of contracts/theming.md, SVG, with a DOCTYPE or entity refused before parsing (`src/svg.ts`); WOFF2 by its header. Over a kind's limit is `file_too_large`. A file that fails is not stored: its path holds the problem until it is replaced or removed, so publish refuses the draft. Anything but an image makes the draft advanced.
  - **CSS** (`src/css.ts`, parsed with `css-tree`, escapes resolved before any name is compared): `css_forbidden` for what does not parse, an at-rule outside `@media`, `@supports`, `@container`, `@layer`, `@keyframes`, `@font-face` and `@charset "UTF-8"` (so `@import`, `@namespace` and `@property` too), a `url()` that is not a package path (`images/…` outside `@font-face`, `fonts/…woff2` inside it: no scheme, `data:`, `//`, absolute path, query or `..`), a string URL in `image-set()`, `image()`, `src()` or `cross-fade()` (and `var()`, `env()` or `attr()` in them, which could fill one in), `local()`, `expression()`, `behavior`, `-moz-binding` and `javascript:` anywhere; at most 256 KB a file and together. Custom properties are parsed too, so a `url()` hidden in one is checked like any. A class neither stable nor `t-` (`src/classes.ts`) is a warning `class_unstable`.
  - **Templates** (`src/template.ts`): the Mustache subset (escaped tags, sections and inverted sections closed within their element, at most 8 deep, comments dropped; no `{{{ }}}`, `{{& }}`, partials, blocks, delimiters or `{{.}}`) inside the HTML subset (`parse5`; the contract's elements and attributes only, no HTML comments, elements at most 32 deep), every failure `template_forbidden`. The `<tbody>` the parser adds around a table's rows is left out of the tree, so a section around rows works with or without an explicit `<tbody>`. Mustache tags are found in the raw text before the HTML is parsed, so an entity never makes one. `class` holds whole names, stable or `t-`, and data only lengthens a literal `t-` name; `src` on `img` is one package image (`images/…`) or one field named `url` or `…_url`, the convention for an image address until the screen contract names each widget's fields. At most 32 KB.
  - **Small text** (`src/readability.ts`, plan D11): each CSS file keeps the `font-size` declarations (and the size of a `font` shorthand) whose selector can apply on the screen surface (not one that names another surface's class; keyframes left out; also inside an at-rule nested in a rule), and every draft change resolves those of the files theme.yaml lists, in its order, for a 1920×1080 screen: `px`, `pt` and the other absolute units, `rem`, `em` and `%` against the last root size the theme sets (a `:root` or `html` selector of a rule's list, not nested and not under `@media` or `@container`, whose condition the check does not read) or else the platform's 16 px, since `<body>` inherits it, the viewport units against 1080 or 1920, absolute keywords, and `calc()`, `min()` and `max()` evaluated, `clamp()` at its minimum; a value with `var()` or a unit it cannot resolve is skipped. Under 27 px is a warning `text_small` on the file, naming the selector (at most 10 a file); a root size is warned about only when it shrinks the platform's 16 px. Like `contrast_low` it is among the draft's `problems`, and publish's 422 lists both with the errors; neither blocks a publish.
  - The package paths a CSS file or template names are kept with it and checked on every draft change: one the package does not hold is `css_forbidden` or `template_forbidden` on the file that names it, until the file is there.
  - `PUT /api/theming/draft/package?draft_version=` (`src/package-routes.ts`): a zip replaces the draft's content, and creates the draft when `draft_version` is absent and there is none (409 `version_conflict` when there is one). The zip is read from memory entry by entry through `yauzl`, never extracted (`src/zip.ts`): absolute paths, `..`, names outside `[A-Za-z0-9._/-]`, a name twice, links and special files, encrypted entries, nested archives (by content and by name), more than 300 files, more than 20 MB unpacked and an unpacking ratio over 100:1 (per entry and in all, from the declared sizes before inflating, with yauzl holding each entry to its declared size) are 400 `package_refused`, as are a missing or unreadable `theme.yaml` (UTF-8, at most 64 KB, YAML with no aliases, a mapping: `src/manifest.ts`) and a path outside the package's folders or over 136 characters (`src/package.ts`). A body over 21 MB is 413 `too_large`. Every file then goes through the checks of one upload of its folder; CSS and templates go through the checks above; an embed is stored only when every file of its folder passes (HTML only as the entry, UTF-8 text, images and fonts through the upload checks, at most 5 MB), and its bytes are reserved like any file, once: a file the draft already holds is not reserved again, and an embed's file that no row keeps any more gives its bytes back (`src/stored.ts`, `Unused`). Changing the embeds needs `theming.embeds.write` and is audited (`theming.draft.embeds_changed`) before the commit.
  - `GET /api/theming/revisions/{revision}/package`: the revision as a package zip (`yazl`), `theme.yaml` and every file at its package path, `no-store`, to `theming.theme.write`; an upload takes it back unchanged.
  - The storage quota (`src/stored.ts`, the kit's `tenantsStorage`): a file new to the event has its bytes reserved at tenants before it is written (413 `storage_quota_exceeded` passed on), identical bytes count once, and a file goes with its bytes when no draft, revision or embed refers to it any more (a file replaced or removed, a draft discarded) or when the write that placed it rolls back. Each container recounts every event's bytes hourly through tenants' repair path, after sweeping files no row keeps and crashed writes' temporary files (`src/upkeep.ts`). Publish's generated CSS and images are not reserved, only counted by the recount, so a publish never fails on the quota.
  - `POST /api/theming/draft/publish` and `POST /api/theming/revisions/{revision}/restore` write the next revision (`src/publish.ts`) under one lock per event's history: its token CSS and admin token CSS, and from `images.logo` (and `images.icon`) the logo as a PNG 512 px wide and the hub's icons (192, 512 and a maskable 512 on `background`, `src/brand-images.ts`; an image that cannot be drawn at a size, such as an SVG a pixel thin and thousands long, is left out rather than failing the publish), are generated then and stored as files, the CSS theme.yaml lists is compiled in its order into one file in `@layer canccu-theme`, generated again from the parsed tree with every `url()` at its served address, and each template parsed into its tree with package images at theirs (`src/compile.ts`; CSS or a template that no longer passes is 422 `theme_invalid`, a restore too), its files and embeds are copied from the draft or the restored revision, and `changed` lists what differs from the revision before. Both need `theming.embeds.write` too when the embeds change, append their audit entry before committing (no audit, no revision) and announce `theming.theme.published` after. A draft with an error is 422 `theme_invalid`; an archived event's writes are 409 `event_archived`.
  - `GET /api/theming/revisions` (newest first, `before`, `limit` up to 100, `pinned` from `theming_pins`: the revision screens are pinned to or the one a timed pin restores) and `GET /api/theming/revisions/{revision}` with its manifest.
  - **Pins** (`src/pins.ts`, plan D12): `screen.pin.changed` sets the event's row in `theming_pins` (`theme_revision` and `restores.theme_revision`), only from an event later than the one it holds (by `time`, then `id`). Each event's screen stream is read from its start when the module starts, so a pin changed while theming was down is learnt then; the kit's bus has no consumer groups, and screen's `GET /api/screen/pin` takes only a session. The freeze itself is screen's (#190): theming honours it by keeping and serving the revisions it pins.
  - **Retention** (`src/retention.ts`): after every publish and restore, after a pin changes and in the hourly upkeep, the revisions older than the newest 20 that no pin keeps are deleted with their file refs, package paths and embed files, under the history lock (a restore or a draft made from a revision copies under it too); each file no draft, revision or embed refers to any more goes with its bytes (`src/stored.ts`). A pruned revision answers 404, also on the internal read.
  - `GET /internal/theming/current?tenant_id=`: the same answer as `GET /api/theming/current` (one function, `currentTheme` in `src/theme.ts`), without the info-page check, so the screens of a `venue_only` or `sign_in` event keep its look; for the screen module only, like the next.
  - `GET /internal/theming/revisions/{revision}?tenant_id=`: one revision resolved like `current`, for the screen module only (its service identity); the tenant must be one the tenants module knows. Internal paths skip the hostname's tenancy: they run in a Fastify scope of their own.
  - `GET /theming/a/<sha256>.<ext>`: a file a revision refers to, public and immutable. Revision 0's token CSS is generated on each read and never stored, so any container serves it by generating it again.
  - `GET /theming/draft/<sha256>.<ext>`: a file the draft refers to, `no-store`, to `theming.theme.write` within the admin address rule.
  - `GET /theming/sandbox/<revision>/<embed>/<path>` and `GET /theming/sandbox/draft/<draft key>/<embed>/<path>`: an embed's files, with the sandbox CSP (`<embed base>` is the embed's folder on the request's own origin; `connect-src 'none'`; `sandbox allow-scripts`), `Cross-Origin-Resource-Policy: cross-origin`, `Access-Control-Allow-Origin: *`, immutable for a revision and `no-store` for the draft. The entry goes only to a frame (`Sec-Fetch-Dest: iframe` or `frame`), every other file only to cross-site requests (an opaque origin's); in IP mode (`CANCCU_IP_MODE=demo`, plain http) that Fetch Metadata rule is skipped. Every response under the path, errors included, sets no cookie, and a refusal is an empty body under `default-src 'none'; sandbox`, so a failed embed paints nothing over the still behind its frame. `GET /api/theming/current` lists each stored embed of the revision with its `frame_url`.
  - Every file response has `nosniff`, `Cross-Origin-Resource-Policy: same-origin` and the content type of its checked type. SVG also has the sandboxing CSP and `Content-Disposition: attachment`.
- **Health:** `postgres`, `valkey` and `files` (the files volume is readable and writable: uploads and the generated token CSS are written there).

## Check

```sh
npm ci && npm run lint && npm run typecheck && npm test
```

`packages/kit-ts` and `packages/ui` need `npm ci` first. The tests need a Postgres for RLS and skip without one. Point `CANCCU_DATABASE_URL` at a throwaway database whose name ends in `_test` (the tests drop and recreate the theming tables, and refuse any other name; [docs/ci.md](../../docs/ci.md#modules)) as a superuser; requests still run as the app role, which RLS binds:

```sh
docker run -d --rm --name canccu-theming-test -e POSTGRES_PASSWORD=test -e POSTGRES_DB=canccu_test -p 127.0.0.1:55433:5432 postgres:17.11-alpine
CANCCU_DATABASE_URL=postgres://postgres:test@127.0.0.1:55433/canccu_test npm test
docker stop canccu-theming-test
```

`test/safety.browser.test.ts` proves in Chromium that theme CSS compiled into `@layer canccu-theme` cannot hide, move, cover or restyle the safety elements of `packages/ui` (the pairing code, the offline marker, the privacy link); it needs no database. `test/sandbox.browser.test.ts` proves the sandbox in Chromium (opaque origin, no storage, no network, no access to the page, the still on failure and under reduced motion) with the level-up demo theme's `drift` embed. Both use Playwright's Chromium where one is installed, else the system Chrome (`channel: "chrome"`, as on CI runners); without either it skips locally and fails in CI. Where the host lacks Chromium's libraries, run them in Playwright's image:

```sh
docker run --rm --network host -u "$(id -u):$(id -g)" -e HOME=/tmp -e CANCCU_DATABASE_URL=postgres://postgres:test@127.0.0.1:55433/postgres \
  -v "$PWD/../..:$PWD/../.." -w "$PWD" mcr.microsoft.com/playwright:v1.64.1-noble npx vitest run browser
```
