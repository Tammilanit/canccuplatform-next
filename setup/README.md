# setup

Scripts for installing a host and keeping the stack up across reboots. The platform runs as one shared stack ([decision 0013](../docs/decisions/0013-multi-tenant-core.md)); events are tenants (rows), so there is no per-event setup here. Every script takes `--dry-run` and fails with a clear message (exit 2) when something is missing or unreachable.

- `install [--dry-run] [--boot]`: checks Docker, writes `deploy/.env` from `deploy/.env.example` (random Postgres password, mode 600), makes sure every module image matches the checkout, starts the stack and checks `/api/hello/health`.
  - **Module images:** install never starts an image built from another commit. Before it starts or enables anything, for every `modules/<name>/Dockerfile` in the checkout it needs `canccuplatform-<name>:latest` (the name Compose gives the images it builds, and what `canccu-stack` starts at boot) with the checkout's `HEAD` in its `org.opencontainers.image.revision` label:
    1. a local image with that label is reused;
    2. otherwise it pulls `<name>:<CANCCU_VERSION>` (`dev`, or the release tag) from the registry the auto-deploy uses (`CANCCU_DEPLOY_IMAGES` in `deploy/.env`, else `ghcr.io/<owner>/<repo>` of the `origin` remote) and tags it `canccuplatform-<name>:latest` if its label is `HEAD`;
    3. otherwise it builds `modules/<name>/Dockerfile` from the checkout (`docker build`, repo root as context, as Compose and the Images workflow do), labelled with `HEAD`.
    - If neither the pull nor the build works, install stops (exit 2) naming the module, before anything is started or enabled. `--dry-run` prints, per module, whether it would reuse, pull or build, and why; it pulls and builds nothing.
    - A checkout with local changes (`git status`) is never paired with a pulled image: every module is built from it, and those builds are labelled `canccu.local-changes=true` too, so they are not reused once the checkout is clean again.
    - Plain install then runs `docker compose up -d --wait --no-build`; `canccu-stack.service` at boot starts the images already tagged and neither pulls nor builds.
  - An existing `deploy/.env` is kept. If it still has the example password (`change-me` or empty), install replaces it with a random one while no database volume exists yet. Once the database exists with it, `--boot` refuses and plain install warns, because Postgres keeps the password it was created with.
  - `--boot` (root, for a host reachable from outside) also installs `canccu-firewall.service` and `canccu-stack.service`, enables Docker, the firewall and the stack at boot, puts the firewall in place **before** the stack publishes its ports, starts the stack through `canccu-stack`, and ends with `check-boot`.
  - Before it changes anything, `--boot` validates `CANCCU_WEB_ALLOW` as the units will see it: from `deploy/.env` only (a `CANCCU_WEB_ALLOW` in the environment is ignored), test-loading the rules. It refuses a checkout path with characters other than letters, digits and `/._-`, because the units bake the path in. The units run `setup/` and `deploy/` as root, so it also refuses them, or the checkout directory, when they are world-writable, group-writable by a group other than `root` or the installing user's own, or owned by anyone but root and the installing user. It writes the `docker` path it found into `canccu-stack.service`.
  - To apply it, install reloads `canccu-firewall` (or starts it if inactive). Never restart that unit: Docker requires it, so a restart restarts Docker and every container on the host.
- `firewall apply|close|remove|check|bypass|status [--dry-run]`: the DOCKER-USER firewall for IPv4 (iptables) and IPv6 (ip6tables).
  - Docker's NAT bypasses ufw, so the `CANCCU-FIREWALL` chain, hooked first into `DOCKER-USER`, drops published traffic unless it comes from a source in `CANCCU_WEB_ALLOW` to port 80 or 443. Container-to-container and outbound traffic are untouched. The final DROP applies to **every** container on the host that publishes a port, not only Caddy.
  - `CANCCU_WEB_ALLOW` lives in `deploy/.env`, never in the repo: a space or comma separated list of IPv4/IPv6 addresses or CIDRs, or `any` to open the web ports to everyone (once HTTPS and sign-in exist). `0.0.0.0/0` and `::/0` work too; a bare `::` is refused. An empty or invalid list makes `apply` refuse without changing anything.
  - `apply` validates every entry (IPv4 octets and prefixes, IPv6 syntax and prefixes; Python's `ipaddress` too when present), then test-loads both families with `iptables-restore --test` and `ip6tables-restore --test`, and only then replaces each chain atomically. It is idempotent. `close` drops all published traffic.
  - `check` exits 0 only if, on both families, `FORWARD` jumps to `DOCKER-USER`, `DOCKER-USER` jumps to the chain and the chain ends in the DNAT DROP rule. That fails on a flushed chain, on Docker's nftables backend, and on IPv6 when Docker's ip6tables support is off (Docker older than 27, or `"ip6tables": false`): the stack then never starts, which is the safe side. `check` also fails on a bypass (below). A closed firewall passes, with a `closed:` line that `check-boot` reports as a failure.
  - A container that calls the host's own public address on a published port also arrives as published (DNAT) traffic from a Docker subnet, and is dropped unless that subnet is in `CANCCU_WEB_ALLOW`. Containers reach each other by service name, which is untouched.
  - IPv6: `deploy/compose.yml` gives the stack's network an IPv6 subnet (a fixed ULA `/64`), so Docker NATs published IPv6 traffic through ip6tables and the chain filters it like IPv4. On an IPv4-only network Docker would instead serve the `::` ports through docker-proxy to the container's IPv4 address; that traffic arrives on INPUT and never meets the chain. `firewall bypass` (no root needed) finds such a docker-proxy for port 80 or 443 and exits 1, and `check` fails on it.
  - Direct routing: a neighbour on the same L2 network could send packets straight to a container address. Docker 28 and later drop those for published ports itself; on older Docker, upgrade.
  - To reach the web ports over Tailscale too, add its ranges (`100.64.0.0/10`, `fd7a:115c:a1e0::/48`) to `CANCCU_WEB_ALLOW`.
- `canccu-firewall.service`: runs `firewall apply` before `docker.service`, and Docker requires it (`RequiredBy=docker.service`), so the rules exist before Docker restores any container. If apply fails it runs `firewall close` and Docker starts with the web ports shut; if even `close` fails, the unit fails and Docker does not start.
- `canccu-stack.service`: after Docker and `canccu-firewall`, checks the firewall (including the bypass) and runs `docker compose up -d --wait`.
- `deploy [--dry-run]` and `canccu-deploy.service` / `canccu-deploy.timer`: auto-deploy of main in dev mode (see [Auto-deploy](#auto-deploy)).
- `check-boot`: checks that Docker, `canccu-firewall`, `canccu-stack` and `canccu-deploy.timer` start at boot, Docker requires `canccu-firewall`, every service has a container that is running, healthy where it has a healthcheck, and has a restart policy (`docker inspect`; no `jq` needed), and the firewall is in place and not closed on IPv4 and IPv6.
- `lib.sh`: helpers `install` and `deploy` share: reading a value from `deploy/.env` and the GitHub repository of the `origin` remote.

`deploy/compose.yml` publishes Caddy explicitly on `0.0.0.0` and `[::]` for ports 80 and 443, because a host's Docker default bind may be `127.0.0.1`. On a host reachable from outside, start the stack only through `setup/install --boot` or `canccu-stack.service`, so the firewall is in place first: plain `setup/install` and `docker compose up` publish on all interfaces with no firewall. A host booted with IPv6 off (`ipv6.disable=1`) cannot bind `::`, so `compose up` fails there.

**Check command:** `setup/test.sh`. It needs no root and changes nothing on the host: every script runs with `--dry-run` or against an unreachable Docker daemon, plus `systemd-analyze verify` on the units, the compose ports and shellcheck (each skipped with a message when its tool is missing). It sources `test-install.sh` and `test-deploy.sh`, its sections for `install` and `deploy`.

## Install checklist
1. If the stack already ran from a version of `deploy/compose.yml` without IPv6 on its network, run `docker compose -f deploy/compose.yml down` first (the volumes stay), so the network is recreated with IPv6.
2. `sudo setup/install --boot`. On a fresh host it writes `deploy/.env` with a random Postgres password and then stops on the empty `CANCCU_WEB_ALLOW`: set it in `deploy/.env` and run `sudo setup/install --boot` again. It pulls or builds the module images for the checkout itself (see Module images above); no `docker compose build` by hand.
3. `sudo setup/check-boot` shows only `ok`.
   - **Auto-deploy is on by default:** `CANCCU_VERSION` is `dev` in `deploy/.env.example`, and `--boot` enables `canccu-deploy.timer`, so the host follows main from then on. On a host that must not, set `CANCCU_VERSION` to a release tag in `deploy/.env` first. For a dev host, also do the steps in [Auto-deploy](#auto-deploy).
4. From an allowed address, `http://<host>/api/hello/health` answers; from any other address it times out, on IPv4 and on IPv6.
5. **Reboot test:** `sudo reboot`. Once it is back, without touching anything:
   - `systemctl status canccu-firewall canccu-stack` shows both active;
   - `docker ps` lists every service healthy;
   - `sudo setup/check-boot` shows only `ok`;
   - health answers from an allowed address and is still blocked from others (IPv4 and IPv6);
   - `sudo ufw status` is unchanged.

## Auto-deploy
In dev mode the host follows main: every merge reaches it a few minutes later, with a health check and a way back. The host pulls; nothing connects to it, so it needs no inbound port and works behind the firewall and Tailscale.

- **When:** only while `CANCCU_VERSION` in `deploy/.env` is `dev`. `CANCCU_VERSION` is the platform version the host runs; it stands for the event repo's `platform.version` until the event repo's deploy word (roadmap step 9) sets it. With any other value `setup/deploy` does nothing and exits 0.
- **How:** `canccu-deploy.timer` runs `canccu-deploy.service` (as root) 5 minutes after boot and then 2 minutes after each run ends. Each run of `setup/deploy`:
  1. refuses (exit 2) a checkout that is not on `main`, has local changes or has diverged from `origin/main`: nobody edits code on the VM;
  2. fetches `origin/main` and pulls `<module>:dev` for every `modules/<name>/Dockerfile` on it, from `ghcr.io/<owner>/<repo>` of the `origin` remote (`CANCCU_DEPLOY_IMAGES` in `deploy/.env` overrides it). A pull that fails stops the run (exit 2) and says why in plain words, with what to do: the registry refused it (a private package and no `sudo docker login <registry>`), the registry cannot be reached (the host's network, DNS or proxy), or the image is not in the registry (the Images workflow did not push it). The registry's own answer goes to the log only;
  3. waits (exit 0) until every image's `org.opencontainers.image.revision` label is that main commit, so code and images always match; the Images workflow ([docs/ci.md](../docs/ci.md#images)) pushes them a few minutes after each merge;
  4. stops when the checkout and the running images are already that commit (exit 0), or when exactly that commit with exactly those images failed before (exit 1, see below);
  5. checks the firewall (`setup/firewall check`), writes down the previous commit and images (`pending`), fast-forwards the checkout and tags each pulled image as `canccuplatform-<module>:latest` (the name Compose gives the images it builds, so `canccu-stack` at boot uses the deployed images too);
  6. runs `docker compose -f deploy/compose.yml up -d --wait --no-build --remove-orphans` (services main dropped are removed) and, when `deploy/Caddyfile` changed, recreates `caddy` (a bind-mounted file is not reloaded otherwise);
  7. checks that every module container runs its new image and that `/api/<module>/health` answers through Caddy for every module within 30 seconds; then it removes the replaced images.
- **On failure** (exit 1): it resets the checkout to the previous commit, tags the previous images back, brings the stack up again (removing services the failed commit added, recreating `caddy` if the Caddyfile changed) and checks its health. Then it opens an issue labelled `module:deploy` on the repo, in the standard issue layout, naming the commit and whether the rollback is healthy (it never includes logs: the repo is public). It holds that commit and those images: one issue per failure, and every later run exits 1 too, so `systemctl status canccu-deploy` stays failed until a new merge or new images arrive and are retried.
- **Interrupted deploys:** if a run stops after it started switching (a reboot, a kill, the unit's 15-minute timeout), the `pending` record is still there. The next run checks that deploy first: healthy on the new commit is kept, anything else is rolled back and reported as above.
- Git runs as the owner of the checkout, never as root, so the checkout stays the owner's. The deploy state (`pending`, the failed commit and images, a lock) is in `/var/lib/canccu-deploy`.
- **Status** (#197): every run that holds the lock writes `status.json` (the time, the commit the checkout runs, `ok` or the error in one line, and how many runs in a row failed since when) to the state directory and to the stack's `canccuplatform_deploy-status` volume, which `deploy/compose.yml` mounts read-only into hello. `/api/hello/health` shows it as the `deploy` check: `ok` with `<commit> deployed; last run ok at <time>`, and after two failed runs in a row `degraded` (HTTP 200: the old version keeps serving and passing health checks) with `failing since <time> (<n> runs in a row): <error>; <commit> still runs`. Every exit 1 or 2 counts, holding a failed deploy included; waiting for images does not. Without `CANCCU_VERSION=dev` the status file is removed, and the check says `no auto-deploy on this host`. The error has no credentials from a URL, but health needs no sign-in, so it is only as private as the firewall makes the web ports.
- Logs: `journalctl -u canccu-deploy`. Run once by hand: `sudo systemctl start canccu-deploy`. Pause: `sudo systemctl stop canccu-deploy.timer` (it starts again at boot unless disabled).

**Set up auto-deploy** (once, on the dev host, after the install checklist):
1. The checkout is a clone of this repo on `main`, owned by an ordinary user, and `git fetch origin main` works for that user.
2. In `deploy/.env`: `CANCCU_VERSION=dev` and `CANCCU_DEPLOY_GITHUB_TOKEN=<token>`, a fine-grained token for this repo only with Issues read and write. Without it a failed deploy still rolls back but opens no issue.
3. If the GHCR packages are private, `sudo docker login ghcr.io` with a token that can read packages (root runs the pulls).
4. `sudo setup/install --boot` installs and enables the timer; `sudo setup/check-boot` shows `canccu-deploy.timer enabled at boot` (checked only while `CANCCU_VERSION` is `dev`).
5. Over Tailscale: add its ranges to `CANCCU_WEB_ALLOW` (above) and open `http://<tailscale-ip>/api/hello/health`.
6. **Shown:** merge a PR to main; once its Images run is green, within a few minutes `journalctl -u canccu-deploy` shows `deployed <sha>, health ok`, and `/api/hello/health` answers `ok`.

Known limits (follow-ups):
- The images' origin is checked only through their revision label. Anyone who can write the GHCR packages could push a `:dev` image labelled with main's commit. Build-provenance attestations checked before tagging, or tighter package write access, would close this.
- If one module's image never arrives (its Images job failed), every run logs `waiting for the images` and exits 0 until the next merge; no issue is opened.
