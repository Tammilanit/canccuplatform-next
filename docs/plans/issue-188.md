# Plan: issue #188, the notify backend and the optional check-in page

Package `notify-checkin`, branch `188-feat-notify-the-notify`. Roadmap step 3; the step's final plan is [docs/briefs/step-3-screen.md](../briefs/step-3-screen.md#plan-final-plan-after-the-session) (D6, D18, P4, principle 7 "check-in is never mandatory"). Sources of truth: `contracts/notify.md` and `contracts/notify.openapi.yaml` (version 1.2.0) as on main at `fea795f`, `modules/admin/declarations/notify.yaml`, the `checkin_qr` widget in `contracts/screen.md`, and [0027](../decisions/0027-product-decisions-2026-11-07-08.md). This plan changes no contract.

## Why a plan first
1. **Size.** #188 is a whole new module: 24 API operations (2 internal), a declarative trigger engine (paths, 7 condition operators, templates with formatters), Web Push with VAPID and `aes128gcm` written against the RFCs, five delivery rules (audience, channels, hourly cap, quiet hours from the run-of-show, urgent), Discord DM requests with the fallback and the bot's guild state, follows with merge and removal, privacy export and delete, archive and retention deletion, rotating check-in codes, the check-in page and the admin topic pages. A full build with tests is about 7,000 changed lines (below), more than four times the package limit of about 1,500 ([AGENTS.md](../../AGENTS.md#how-work-flows)). The package plan already said so; workers may not split an issue, so the lead decides the split. #50 and #187 went the same way ([issue-50.md](issue-50.md), PR #204).
2. **Identity.** "Sign in once" on the check-in page, "current members" (the `attendees` audience, `403 not_a_member` on check-in) and the Discord id behind a DM all come from work that is still open: the central sign-in with tenant-bound sessions (#52) and members and the internal user read (#150). Today the only session is admin's, and admin's sign-in has no return path, so a check-in page on `/notify/` cannot send someone to sign in and bring them back. How #188 behaves before #52 and #150 is a decision (Q2, Q3), not a detail.

## Design (holds for every split)
| # | Decision | Reason |
|---|---|---|
| D1 | Python 3.12, Starlette, asyncpg, uvicorn on `canccu-kit[starlette]`, the same pins and layout as `modules/tenants` (`db.py` with `SET LOCAL ROLE canccu_notify_app`, `deps.py`, `app.py`, routes split by area: `registry.py`, `config.py`, `engine.py`, `templates.py`, `push.py`, `webpush.py`, `subscriptions.py`, `delivery.py`, `quiet.py`, `dm.py`, `inbox.py`, `me.py`, `checkin.py`, `pages/…`) | One Python toolchain; tenants and the agenda plan use the same patterns, and no file passes about 400 lines |
| D2 | Web Push is written on `cryptography` (already the kit's dependency): ECDH P-256, HKDF-SHA256 and AES-128-GCM for RFC 8291, an ES256 JWT for RFC 8292, sent with `httpx`. The encryption is tested against RFC 8291's own example (Appendix A) and end to end against a fake push service that decrypts with the subscription's private key | About 150 lines instead of `pywebpush`, which pulls in `requests`, `py-vapid` and `http-ece`; the RFC vector proves interoperability without a real push service (D18: "tested with a fake push service") |
| D3 | The VAPID private key comes only from `CANCCU_NOTIFY_VAPID_PRIVATE_KEY` (base64url raw P-256 scalar); the public key is derived from it. Without a valid key the module refuses to start with a clear message (the kit's `ConfigError`), as admin does with a bad `CANCCU_PUBLIC_URL`. A one-off `python -m canccu_notify vapid-keygen` prints a key for `deploy/.env`; CI's demo stack generates one per run | Contract, Web Push: a secret in the environment, never in a setting or the database. The contract has no error for "push is off", so starting without push would leave `GET /api/notify/push-key` with no answer it allows; adding one would be an additive contract PR first |
| D4 | Subscriptions store the push `endpoint` in clear (it is the replace key) and the `p256dh` and `auth` keys sealed with the kit's `SecretBox` (associated data `notify:sub:<tenant>:<id>`); the subscription token is 32 random bytes, stored as SHA-256 and compared in constant time | The keys let anyone push to the phone; secrets at rest follow 0013 item 29 |
| D5 | The check-in key per event is 32 random bytes made on the event's first code request, sealed with `SecretBox` (associated data `notify:checkin:<tenant>`) in a per-tenant row. No code is stored; the archive deletes the key with the rest | Contract: "a per-event key", "no code is stored"; a random key per event, unlike one derived from a platform secret, cannot be recomputed for another event if one key leaks |
| D6 | The trigger engine is pure (`envelope`, `registration`, `config`, `now`, time zone → candidate notifications) and has no I/O; the consumer around it does the dedupe insert (`INSERT … ON CONFLICT DO NOTHING` on `(tenant, topic, key)`), the notification row and the delivery jobs in one transaction, and publishes or pushes after the commit | Every rule of Topic registry is testable as a table of fixtures; at-least-once delivery cannot create two notifications |
| D7 | Delivery runs from rows, not memory: one `deliveries` row per recipient, channel and notification (`pending`, `held`, `sent`, `capped`, `failed`, `skipped`), claimed by a loop in every container with `FOR UPDATE SKIP LOCKED`. The cap counts `sent` rows of the recipient in the last 60 minutes (a push and a DM of one notification count once); quiet hours turn non-urgent rows `held`, and their end releases the newest unexpired held row per topic per recipient and leaves the rest in the inbox | Containers keep no state and may run more than once; a restart during quiet hours keeps them |
| D8 | Quiet hours are kept as a mirror of the agenda's `quiet_hours` items (id, visibility, status, `starts_at`, `ends_at`, `agenda_version`), fed by the agenda events and re-read from `GET /api/agenda/items` as a module on start, on `agenda.items.cloned` and when `agenda_version` jumps. While the agenda module does not exist (#187), tests use fixtures checked against `contracts/agenda.md`, and an unreachable agenda keeps the last mirror and logs it | The contract's rule, and "fail graceful" when the agenda is down |
| D9 | DMs are requested only while the event's bot state (from `bot.guild.bound`, `.unbound`, `.client.changed`) is bound and not `paused` or `failed`. Until the bot module exists no event arrives, so no DM is ever requested and the push and inbox work alone | Contract, Discord DMs: the bot decides whether a DM can go out |
| D10 | The callers: a session through the kit's `RightsChecker`, a subscription through `Authorization: Bearer`, a module through the kit's `ServiceIdentity` on `/internal/notify/` (the internal network guard stays as for every internal path, D12 of the step plan) | The kit's existing patterns; #157's module identity is already in the kit |
| D11 | Check-in is an extra, never a gate: no Notify path reads check-ins except `GET /api/notify/check-ins/mine`, the export and the check-in page; no topic, inbox entry or banner asks anyone to check in. Area N's tests run every guest and member path of the module with and without a check-in and compare the answers | Principle 7 and 0027; the test is the proof the criterion asks for inside Notify |
| D12 | Pages (the check-in page and the admin topic pages) are server-rendered by Notify (`/notify/check-in`, `/notify/admin/topics`; Caddy strips `/notify`), phone-first, styled with `packages/ui`'s tokens under the event page CSP, forms that work without JavaScript. The hub PWA itself stays the App track's | Like admin's and the agenda's pages; no new frontend stack before the App track |

Notify's tests carry the contract's registrations as fixtures (`schedule` in full, the others as the table lists them, provisional names marked), and a test checks the `schedule` fixture against the JSON in `contracts/notify.md` | "Notify knows no topic in its code" |

## Questions
Question: **Q1, the split.** Build #188 as one PR of about 7,050 lines, or split it? **Recommendation:** the five packages above, as five issues that replace #188 (1 → 2 → 3; 4 and 5 after 1), each with its share of #188's criteria: the first criterion spread over 1–3, check-in and "never mandatory" in 4, the admin pages in 5.

Question: **Q2, "sign in once" before #52.** Admin's sign-in (`/admin/sign-in`) has no return path and its session is not bound to a tenant, so the check-in page cannot send someone to sign in and come back. Options: (A) package 4 waits for #52, whose hand-off returns to the page; (B) package 4 adds a `next` parameter to admin's sign-in (a same-origin relative path only, kept in the signed `canccu_sign_in` state cookie, never an absolute URL), which is a change to sign-in code in admin, high risk, inside package 4; (C) the page shows "sign in on this phone first" with a link to `/admin/sign-in` and the attendee scans the QR again (the code is valid for at most two periods). **Recommendation:** B. It makes the round trip work end to end in step 3, as D6 asks, and #52 later replaces the target of the same link. If the lead prefers no change to admin's sign-in before #52, then A.

Question: **Q3, members and Discord ids before #150.** The tenants module has no membership read and no `GET /internal/tenants/users/{user_id}` yet. **Recommendation:** the same rule as the agenda plan's Q3: until #150 every valid session on the event's hostname counts as a member (today only organisers and crew have sessions), behind one function `is_member(tenant, user)` that switches to the tenants read when #150 lands (a `Follow-up:`). The Discord id for a DM is read from the tenants internal user read only; while it answers 404 the DM is not requested and the reason is logged. Alternative: no `attendees` notifications and no check-ins at all until #150 (every check-in is 403 `not_a_member`), which makes the check-in QR fail end to end in step 3.

Question: **Q4, the admin pages and the never-mandatory proof across modules.** The "Event" menu is planned in the agenda's package 3 (#187, its D9). **Recommendation:** package 5 adds "Notifications" to that group and therefore follows the agenda pages; if it runs first, it adds the group itself in the same shape. The criterion "tests prove a person who never checks in sees every public page and screen" is proved inside Notify by D11; the screen and the agenda have no check-in dependency in their contracts, and a cross-module test belongs to the demo-stack screenshots (#191) once the player exists (a `Follow-up:`).
