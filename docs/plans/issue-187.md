# Plan: issue #187, the agenda module (the run-of-show)

Package `agenda-run-of-show`, branch `187-feat-agenda-the-run`. Roadmap step 3; the step's final plan is [docs/briefs/step-3-screen.md](../briefs/step-3-screen.md#plan-final-plan-after-the-session) (the live-editing requirement, U9, E7, D5, D17, P4). Sources of truth: `contracts/agenda.md` and `contracts/agenda.openapi.yaml` as on main at `fea795f`, plus the `schedule` topic in `contracts/notify.md` and the tournament session events in `contracts/events.md`. This plan changes no contract; question Q2 proposes one additive contract PR.

## Why a plan first
1. **Size.** #187 is a whole new module plus its pages: 11 API operations (clone aside), 11 event types, a per-tenant reminder scheduler, the tournament-session mirror, and phone-first pages with quick-add, templates, change previews, "show on screens now", undo and merge of concurrent edits. A full build with tests is about 4,900 changed lines (below), more than three times the package limit of about 1,500 ([AGENTS.md](../../AGENTS.md#how-work-flows)). The package plan already said so; workers may not split an issue, so the lead decides the split. This is the same situation as #50 ([issue-50.md](issue-50.md)).
2. **One criterion needs a contract addition.** "Show on screens now, and an optional announcement in the same step: a Notify notification (step 3)" has no event in the agenda contract that Notify turns into a notification: the `schedule` topic triggers only on reminders, delays and cancellations, and the `announcements` topic belongs to step 4's announce action. A contract change is its own PR and merges first ([Contracts](../../AGENTS.md#contracts)), so the build of that criterion waits for it (Q2).

## Design (holds for every split)
| # | Decision | Reason |
|---|---|---|
| D1 | Python 3.12, Starlette, asyncpg, uvicorn on `canccu-kit[starlette]`, the same pins and layout as `modules/tenants` (`db.py` with `SET LOCAL ROLE canccu_agenda_app`, `deps.py`, `app.py`, routes split by area) | One Python toolchain; tenants already has the RLS, migration-role and test patterns |
| D2 | Every write is one transaction: the item change, `revision` +1, `agenda_version` +1 (a per-tenant counter row taken `FOR UPDATE`, so versions never skip or repeat), the change-log row, and the item's pending timers replaced. Events are published after the commit, in order | Contract, Editing live; a consumer that sees a gap re-reads |
| D3 | The starter kinds are inserted for a tenant on its first agenda request or event (`INSERT … ON CONFLICT DO NOTHING`, `kinds_version` 0), never by a cross-tenant job | Tenant data appears only in the tenant's own context (0013) |
| D4 | Timers are rows (`item_id`, `kind` reminder/started/ended, `lead_minutes`, `due_at`), rewritten from the item on every change; a loop in each container claims due rows with `FOR UPDATE SKIP LOCKED` per tenant and publishes. A timer more than a few minutes late after an outage still fires `started`/`ended` but drops reminders whose start has passed | Containers keep no state and may run more than once; "a lead that has already passed is skipped" |
| D5 | Delay with `following` takes every scheduled item with `starts_at` ≥ the item's old start except `quiet_hours`, checks every shifted item before writing anything (400 `invalid_request` for an end at or before its start), and emits one `agenda.item.delayed` per item with one `correlation_id`, sorted by new `starts_at` | Contract, Editing live |
| D6 | Visibility: a guest gets `public` items only when `check_info_access(viewer="guest")` passes; any valid session on the event's hostname counts as a member until the tenants membership API lands (#150, Q3); `agenda.crew.read` adds `crew` | The contract's reading rules with today's kit |
| D7 | The tournament mirror applies a session event only when `session.revision` is newer than the stored one, keeps a tombstone per removed session, and is tested with fixtures whose shape is validated against `contracts/events.md`'s `Session` (a JSON fixture per event type, checked by a test that reads the catalog) | D17: the mirror runs on fixtures until step 7 |
| D8 | Pages are server-rendered by the agenda module under `/agenda/` (Caddy strips the prefix), phone-first (one column, 44 px targets, sticky action bar), styled with `packages/ui`'s tokens through the event page CSP (`event_page_csp(..., page="admin")`), forms that work without JavaScript plus a small script for the preview | Like admin's pages; Live from a phone; no new frontend stack |
| D9 | Admin's navigation gains an "Event" group whose first entry is "Run of show" (`/agenda/`), shown to a session holding `agenda.items.write` or `agenda.crew.read`; later modules add their pages to the same group | P4: the event pages sit under one "Event" menu |
| D10 | Previews are computed by the same functions that apply the change, run in a transaction that is rolled back: the list of items that move (old → new times), those that do not and why (quiet hours, started, cancelled, managed), and per item the channels in effect from `notify_channels`, the `schedule` topic's rule (delays and cancellations within 120 minutes) and the bot's channel post | "Preview before anything changes" can never disagree with what the change does |
| D11 | Templates are agenda data for the pages only (not in the API): name, kind, default length in minutes, location, zone, visibility, `reminder_leads_minutes`, `notify`. A new event gets three starter templates (Food → `meal` 60 min, Ceremony → `ceremony` 30 min, Game session → `activity` 120 min), all editable. Quick-add picks a template or a kind; "now" means the next whole minute, "in 30 min" is a chip, a time is a time picker in the event's time zone | The criterion's templates carry a default length, which a kind does not have; keeping them page data avoids a contract change |
| D12 | Undo: each page action stores its inverse for 2 minutes (a delay → the opposite delay of the same items whose revision has not moved since; an add → remove; a move or edit → the old values; a cancel or remove → the item added again, as the contract says cancelling is final). Undo runs through the normal writes, so it emits normal events, and the page says "people who were told will be told again". An inverse that would touch an item changed since is refused with who changed it | U9; the contract keeps "cancel is final" |
| D13 | Concurrent edits: the change log records `actor_user_id`, the session's display name, the fields and the old and new values per revision. A page edit sent with a stale revision is re-applied on the current one when its fields do not overlap the fields changed since; otherwise the page shows who changed what and the current values. The API itself keeps 409 `version_conflict` as the contract says | E7; the merge lives in the pages, so the contract stays unchanged |
| D14 | "Show on screens now": an item still ahead is brought forward to now with a delay (without `following`), so screens show it in now/next at once and its planned time stays visible; a running item is already shown. The optional announcement is Q2 | Uses the contract's delay; every screen, the bot and the hub follow `agenda.*` |

## Questions
Question: **Q1, the split.** Build #187 as one PR of about 4,950 lines, or split it? **Recommendation:** the four packages above, as four issues that replace #187 (1 → 2 → 3 → 4), each with its share of #187's criteria. If the lead prefers fewer: merge 3 and 4 into one package of about 1,800 lines after the Q2 contract PR has merged.

Question: **Q2, the announcement of "show on screens now".** Nothing in the contracts turns it into a Notify notification in step 3. Options: (A) an additive contract PR first: a new event `agenda.item.announced` (`item`, `message` (optional, ≤ 140 characters), `agenda_version`, `actor_user_id`), a fourth trigger on the `schedule` topic for it (audience from `data.item.visibility`, `channels_field` `data.item.notify_channels`, title `{data.item.title}` and body `{data.message}`, expiring at `data.item.ends_at` or after 60 minutes), and the bot posting it on `discord_channel`; (B) no contract change: the bring-forward delay of D14 already triggers the `schedule` topic's "moved, now at…" notification, but only for an item that was still ahead, and never with the organiser's own words; (C) leave the announcement to step 4's announce action. **Recommendation:** A. It is additive, so normal risk, and it is the only option that meets the criterion as the session wrote it.

Question: **Q3, members before #150.** The tenants module has no membership API yet, so the agenda cannot tell a member from any signed-in user. **Recommendation:** until #150, every valid session on the event's hostname reads `attendees` items (today only organisers and crew have sessions), and the check becomes the tenants membership read when #150 lands (a `Follow-up:`). Alternative: `attendees` items are readable only with `agenda.crew.read` until then, which hides them from attendees who later sign in.

Question: **Q4, the starter templates and the menu.** **Recommendation:** the three templates of D11 and the "Event" group of D9 as described; both are page data the organiser changes, so they need no decision record.
