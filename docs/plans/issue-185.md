# Plan: issue #185, the theming module and the brand kit

Package `theming-brand-kit`, branch `185-feat-theming-the-theming`. Roadmap step 3; the step's final plan is [docs/briefs/step-3-screen.md](../briefs/step-3-screen.md#plan-final-plan-after-the-session) (L4, L5, L7, E5, O5, D14, D15, D16, P1, P4, and the brand-kit flow). Sources of truth: `contracts/theming.md`, `contracts/theming.openapi.yaml` (1.2.0) and `contracts/theme.schema.json` as on main at `2327403`, which includes the storage quota of #231. This plan changes no contract; questions Q4 and Q5 name two small contract gaps.

## Why a plan first
1. **Size.** The package plan already says this issue alone passes the package limit. In numbers it is about 8,800 changed lines (below), almost six times the limit of about 1,500 ([AGENTS.md](../../AGENTS.md#how-work-flows)). Workers may not split an issue, so the lead decides the split, as for #108 ([issue-108.md](issue-108.md)) and #187 ([issue-187.md](issue-187.md)).
2. **No theming module and no legacy to port.** `modules/theming/` does not exist, and the legacy repos have no theme system at all (the only hits are a retro-terminal look in the signup site and the ticker's four presets in canccusignage, both inventoried as "reuse with changes" for the demo theme's tokens and fonts, already done). Everything here is "invent" in the brief's sense: new code with new tests.
3. **Untrusted uploads.** Most of the size is the upload checks the contract demands (zip, CSS, SVG, raster, WOFF2, templates). Each is security code; bundling all of it with the pages and the brand kit would make one very large high-risk review.
4. **Two criteria have no contract yet,** and one criterion overlaps another issue:
   - "Publishing an advanced theme **warns when text falls under 2.5 %** of the screen height": the contract has `contrast_low`, but no problem code for small text (Q4).
   - "Publishing changed CSS **requires a preview first**": the API's publish has no such refusal (Q5).
   - "**Freeze for the event**" pins through `PUT /api/screen/pin`, a screen path, and #190 (Studio planning) lists "Pins and freeze for the event" as its own criterion (Q3).
5. **CI is `.github/`.** The new module's checks need steps in `.github/workflows/ci.yml` (as #50, #187 and #108's plans found), which makes the package that adds them high risk regardless.

## Design (holds for every split)
| # | Decision | Reason |
|---|---|---|
| D1 | **TypeScript:** Node 22, Fastify 5, `pg`, vitest, on `@canccu/kit` with `@canccu/kit/fastify`, the pins and lint setup of `modules/screen` | [0006](../decisions/0006-stack.md) makes TypeScript the default; the screen module, the player (#109) and `packages/ui` that render the theme are TypeScript, so the template renderer and the token CSS are shared code, not two ports |
| D2 | **Libraries for untrusted input:** `yauzl` (zip, read entry by entry with a byte budget, never extracted to disk by path), `sharp` (raster decode and re-encode; SVG to PNG for `logo_png_url` only after the SVG check), `css-tree` (CSS), `parse5` (template HTML), `saxes` (SVG as XML with DOCTYPE refused before parsing), `ajv` (2020-12), `yaml` with `maxAliasCount: 0` | Parsers with no network or file access; refusing DOCTYPE and YAML aliases first closes entity and alias bombs |
| D3 | **One write path:** every draft change (file, tokens, brand, layout, package, mode) loads the draft `FOR UPDATE`, checks `draft_version` (409 `version_conflict`), applies the change, re-runs the whole check set on the result, stores the problems and bumps `draft_version` and `draft_key` in one transaction; files are reserved and written before the transaction and released when it rolls back | Problems always describe the stored draft; the quota never drifts on a failed write |
| D4 | **Revisions are immutable rows** with the compiled CSS, token CSS and admin token CSS stored as files at publish, so `current` and the internal pinned read are pure reads of addresses | Screens cache immutable addresses offline ([0013](../decisions/0013-multi-tenant-core.md) item 25); a pinned revision draws the same forever |
| D5 | **Brand-kit generation** works in OKLCH: a given colour that fails as text is moved in lightness only, in fixed steps, until it passes; `primary_text` is the first of `background`, white and black that passes on both fills; status colours start from the platform defaults and are moved the same way; the result is rounded to `#rrggbb`. Golden tests pin the output of a table of inputs | "Deterministic … screenshots stay stable"; lightness-only keeps the hue the organiser chose |
| D6 | **Dark or light** (`scheme`) chooses `background`, `surface`, `border`, `text`, `text_muted` from two fixed platform palettes before the shade search; dark is the default | L5 |
| D7 | **Starting points** (L4): the three demo packages are copied into the image at build time from `events/demo/themes/` and offered by the brand-kit page, which uploads the chosen one with `PUT …/draft/package` | No contract change; the demo themes are already checked by `scripts/check-theme-refs` and CI screenshots |

## Questions
Question: **Q1, the split.** Build #185 as one PR of about 8,800 lines, or split it? **Recommendation:** the nine packages above (slice 0 a contract package), as issues that replace #185, each with its share of #185's criteria; #186 (embeds) then depends on slice 6, and #191 (CI screenshots) on slice 8.

Question: **Q2, the stack.** TypeScript (D1) or Python like admin and agenda? **Recommendation:** TypeScript, by 0006 and because the template renderer and the token CSS are shared with the screen player and `packages/ui`.

Question: **Q3, "freeze for the event".** The freeze pins through `PUT /api/screen/pin` (screen's path, right `screen.bundle.write`), and #190 lists "Pins and freeze for the event" as its own criterion. **Recommendation:** theming's share is to keep and serve pinned revisions (slice 7, D12); the switch and its page stay in #190, and #185's criterion is read as "theming honours the freeze". Alternative: the brand-kit page also gets a "freeze" button that calls screen's pin path, once the screen module serves it.

Question: **Q4, the small-text warning.** The contract has no problem code for text under 2.5 % of the screen height. **Recommendation:** an additive contract PR (slice 0): a warning code `text_small` ("text under 2.5 % of the screen height (27 px at 1080p) on the screen"), checked statically as D11 describes, listed with `contrast_low` among the warnings publish returns; CI's rendered check stays #191's.

Question: **Q5, "publishing changed CSS requires a preview first".** **Recommendation:** enforce it in the pages only (D10), with no contract change: it guards against a mistake, not an attacker, and anyone with `theming.theme.write` could open the preview anyway. Alternative: slice 0 adds a `previewed_version` to the draft, set by a `POST …/draft/preview/seen`, and publish answers 409 `preview_required` when the CSS changed and it is stale.

Question: **Q6, the storage quota before tenants serves it.** **Recommendation:** slice 3 waits for tenants' reserve and release (the #231 contract is merged; its implementation is a tenants issue). Alternative: slice 3 ships with D13's stub and a `Follow-up:`, so uploads are bounded only by the package limits until then.

## After the answers
The lead rewrites #185 and opens the slice issues as the answers decide; each slice then runs as a package against this plan's design table, test-first: real Postgres for RLS and the cross-tenant leak tests of drafts, files and revisions (`assertTenantIsolation` for every per-tenant table), a memory bus for `theming.theme.published` and `screen.pin.changed`, hostile fixtures for every check (zip slip, symlink, nested zip, zip bomb by size and ratio, polyglot files, SVG with entity, script, `foreignObject` and external `href`, CSS with `@import`, `data:` and `expression()`, templates with `{{{ }}}`, `on*`, `style` and `href`), the headers and CSP of every served path, and golden tests for the brand kit. Before each PR: `npm run lint`, `npm run typecheck`, `npm test` in `modules/theming` (and `packages/ui` for slice 7, `modules/admin` for slice 8), `scripts/check-tenancy`, `scripts/check-naming`, `scripts/check-file-size`, `scripts/check-contracts`, `scripts/check-theme-refs`, and the demo stack: `/api/theming/health` ok and `GET /api/theming/current` through Caddy. No source file over about 400 lines: one file per check (`zip.ts`, `svg.ts`, `raster.ts`, `css.ts`, `template.ts`, `manifest.ts`) and routes by area.
