# Plan: issue #223 — the screen crew role preset

Package `admin-screen-crew-preset`, branch `223-feat-admin-the-screen`. Step 3, slice F of the accepted #107 plan ([issue-107.md](issue-107.md)). Sources of truth: `contracts/admin.md` (Granting rights) and `contracts/admin.openapi.yaml` as merged in #231 (G3), `contracts/screen.md` (Rights), `contracts/tenants.md` (Users, roles and membership), and admin, tenants and the kit as on main at 08e74bc. This plan changes no contract and no code. It names what the slice needs that main does not have yet, so the lead can settle it first.

## Why a plan first
The #107 plan gave slice F one dependency, G3, which is now merged. Three more facts on main stop the slice from meeting the contract:

1. **Admin cannot learn whether the target user is a member, or an event admin.** `GET`/`PUT /api/admin/rights/{user_id}` answer 404 `not_found` for a user who is not a member of the event, and report `event_admin`. Membership is the tenants module's (#150, open): main has no members, no `GET /api/tenants/me`, no `GET /api/tenants/current/admins`, no `/internal/tenants/users/{user_id}` and no `tenants.member.*` events. Even once #150 lands, no contract path lets a module ask about *another* user. The user-facing paths need `tenants.members.read`, which a holder of `admin.rights.write` may not have. Events are the only other source, and the kit reads them from `$` (`Bus.subscribe_tenants`), so admin loses whatever happens while it restarts. A rights check built on that is not safe.
2. **Admin cannot tell whether the caller is an event admin of the request's event.** The `PUT` needs the caller to "hold every right the change adds or removes", and an event admin holds every right. Admin's sessions carry only its own global roles (`ROLE_RIGHTS` in `auth.py`: owner and admin, `admin.*` rights only). So today even the owner lacks `screen.devices.read` and could not grant `screen_crew`. The event-admin role lives in the tenants module's `event_admins`. The contract does give the caller's own role: `GET /api/tenants/me` with the caller's cookie answers `roles` and `member` (tenants.md, Users, roles and membership). That path needs #150 but not G6. Even so, F3 asks G6 about the caller too: one source for caller and target, and admin need not forward the caller's cookie and hostname to the tenants module.
3. **A granted right reaches no session until sessions are bound to a tenant (#52, open).** A session's `rights` should be the role's plus those granted in the session's event. Admin's sessions have no tenant (`admin_sessions`), and modules call `GET /api/admin/session` on `admin:8080`, where no hostname names one. Without #52, a grant is stored and audited but no module sees it.

Building the slice anyway would mean making up a membership rule in high-risk rights code (for example "every user admin has seen is a member"). That is a contract decision, outside a worker's Room to design ([AGENTS.md](../../AGENTS.md#issues)).

## Proposed contract gap
| # | What is missing | Proposed additive change |
|---|---|---|
| G6 | A module asks whether a user is a member of an event and holds its event-admin role | `GET /internal/tenants/tenants/{tenant_id}/users/{user_id}` → `{"member", "event_admin", "joined_at"}`. Internal network only, like `GET /internal/tenants/tenants/{tenant_id}` and every `/internal/tenants/` path (tenants.md, Resolving the tenant). `joined_at` is the time of the current membership, set anew on every join, and `null` when `member` is false (F5 binds a granted list to it). A `?tenant_id=` on `GET /internal/tenants/users/{user_id}` would also work, but that path answers the whole `UserInternal` (Discord id, identities), more personal data than a rights check needs |

## Design (once G6 and #150 are in)
| # | Decision | Reason |
|---|---|---|
| F1 | **Table** `admin_tenant_rights (tenant_id, user_id, rights text[], rights_version integer, member_since timestamptz)` under RLS, like `admin_tenant_settings`, primary key `(tenant_id, user_id)`; migration `004_tenant_rights.sql`, additive. `member_since` is G6's `joined_at` when the list was last written. A list taken away is emptied, never deleted (except under F6's deletions). No row means an empty list and `rights_version` 0 | The contract's `rights_version` keeps counting across leaving and rejoining |
| F2 | **Presets** as code: `PRESETS = {"screen_crew": ("screen", [...6 rights])}` in `rights.py`, with a test that compares it to `contracts/screen.md` (Rights). The test reads only the paragraph that starts `**The "screen crew" preset:**`, takes its first sentence, and collects the backticked tokens there that match `<module>.<right>`. Other wording in the paragraph cannot break it | The contract names the list; a test keeps code and contract equal. A machine-readable preset list in `contracts/` would be sturdier (Follow-up) |
| F3 | **`PUT` checks, in order:** signed in → `admin.rights.write` (or event admin) → each right matches `<module>.<right>` and names a module admin knows (`MODULES` in `app.py`), else 400 `invalid_request` → no role-only right (400 `right_role_only`, the three from tenants.md) → G6 says member (404) → the caller holds every right in the symmetric difference of old and new (403 `missing_right`; event admin holds all) → event not `archived` (409 `event_archived`) → an upsert, `INSERT … ON CONFLICT (tenant_id, user_id) DO UPDATE … WHERE admin_tenant_rights.rights_version = $sent`, where a missing row stands for version 0 and a matched-nothing write is 409 `version_conflict`. `GET` runs the same first steps up to the membership check and answers F5's list | The contract's codes. Membership comes before the `missing_right` check, so a caller who may grant learns nothing about a non-member's list from a 403. The module check stops typos in the module part; a right no contract defines (`screen.devise.write`) can still be stored, because no machine-readable list of every right exists yet (Follow-up) |
| F4 | **Audit before commit:** G6 is asked before the transaction opens. Inside it: lock the row, check the version, write, then `POST /internal/tenants/audit` (action `admin.rights.changed`, `changes` old and new) with a 5 s timeout, then commit. A failed or timed-out append rolls the change back. After the commit, `admin.rights.changed` goes to the tenant's stream, not the platform stream. **Trade-off:** if the commit fails after the append, the log holds an entry for a change that never happened. That is accepted: the reverse, a change with no entry, is not. The row lock is held for one audit round trip at most | "Audited in the same request"; the event concerns one event |
| F5 | **A granted list belongs to one membership.** `granted_rights(tenant_id, user_id)`, the read that `GET` and #52's session use, counts the stored list only while G6 says `member` and its `joined_at` equals the row's `member_since`. If the user is no member, the answer is empty. If they are a member with another `joined_at` (they left, admin missed `tenants.member.left`, and they rejoined), the read empties the list in the store, raises `rights_version` and emits `admin.rights.changed` with `[]`, as F6 does. So a missed event never leaves rights on someone who left, nor gives them back on rejoining. A write read before the member left is stale after they rejoin, as admin.md asks | Defence in depth against the kit's `$` reads (point 1) |
| F6 | **Following tenants.** On the tenant streams (`Bus.subscribe_tenants(["tenants"])`): `tenants.member.left` empties the list, raises `rights_version` and emits `admin.rights.changed` with `[]`; `tenants.admin.removed` changes nothing; `tenants.retention.reached` with `data_class: "personal"` deletes the tenant's rows (the event is archived, so no write follows that would need the version). On the platform stream (`Bus.subscribe(["tenants"])`): `tenants.tenant.deleted` deletes the tenant's rows in that tenant's scope; `tenants.user.deleted` handles the user in every tenant that has a row for them. Under per-tenant RLS that needs one narrow cross-tenant read: a `SECURITY DEFINER` function owned by the migration role, `admin_rights_tenants_of(user_id)`, that returns tenant ids only, after which each tenant is handled in its own `tenant_transaction`. admin.md says the list is emptied on user deletion, tenants.md that every module deletes the user's rows; F6 follows whatever the lead settles (Follow-up; recommendation: delete, since a deleted user never rejoins) | The contract's Granting rights and retention rules |
| F7 | **Tests:** every path with each code above; a first grant to a member with no row (version 0) succeeds; the preset round trip (`GET` presets, one `PUT`, then one right taken away alone); a member leaves while admin misses the event, rejoins, and the list is empty with a higher `rights_version`; each F6 handler (member left, personal retention, tenant deleted, user deleted across two tenants); a failed audit append leaves the list unchanged; cross-tenant leak tests (a grant in event A is invisible and unchangeable from event B's hostname); the Postgres store under RLS and the cross-tenant function in `test_store_pg.py` | As the slice's high risk asks |

About 650 changed lines with tests.

## Questions
1. **Membership lookup:** add G6 as proposed, as a contract PR before this slice and built by the tenants module with #150? Or does admin keep its own copy of membership from tenants events, with a durable cursor in the kit? Recommendation: G6. A synchronous answer cannot drift, and the kit has no durable cursor.
2. **Order:** block #223 on #150 and the G6 contract PR? Recommendation: yes. Nothing in the slice can return a correct 404 or `event_admin` before then.
3. **The session merge:** does #52 (which binds sessions to a tenant) add the granted rights to `GET /api/admin/session`, or a short slice after #52? Recommendation: #52, since that is where a session first knows its event. #223 leaves the `granted_rights` read (F5) for it, with tests.
4. **Owner and admin roles:** admin's global `owner` and `admin` roles predate tenancy. Until #52 replaces them, should `ROLE_RIGHTS` stay as it is, so only an event admin (through G6) can grant `screen_crew`? Recommendation: yes. A global role that holds every module's right would hold it in every event.

## Answers (the lead, 2026-11-09)
All four as recommended:
1. **Membership lookup:** G6 as proposed, as the contract issue #248. The tenants module serves it with #150.
2. **Order:** #223 is blocked by #150 and #248.
3. **The session merge:** #52 adds the granted rights to `GET /api/admin/session` (noted on #52). The lead's words: "#223 leaves F5 to it, with tests". This plan reads that as the recommendation put it: #223 builds the `granted_rights` read (F5) with its tests, and #52 calls it from the session.
4. **Owner and admin roles:** `ROLE_RIGHTS` stays as it is until #52. Only an event admin, as G6 reports, can grant `screen_crew`.
