# CI

`.github/workflows/ci.yml` and `.github/workflows/demo-stack.yml` run on every pull request, merge-queue entry and push to main; `demo-stack.yml` also runs nightly and by hand, and runs only what a change needs (see [Tiers](#tiers)). `.github/workflows/release.yml` builds the module images (see [Images](#images)). `.github/workflows/review-gate.yml` runs on pull requests, PR comments and merge-queue entries. There is no Claude review in CI (see [Code review](#code-review)).

## Checks (names are stable; branch rules require them)
| Check | What it does |
|---|---|
| `lint-types-test (kit-ts)` | `scripts/check-module packages/kit-ts` with its own Valkey and Postgres, set up as a module job is (see [modules](#modules)): `npm ci`, `npm run lint` (eslint + prettier), `npm run typecheck`, `npm test` (vitest), the integration tests included. |
| `lint-types-test (kit-py)` | `scripts/check-module packages/kit-py` with its own Valkey and Postgres: `pip install -e ".[dev]"`, `ruff check .`, `ruff format --check .`, `mypy .` (strict), `pytest`, the integration tests included. The `dev` extra pins these tools. |
| `lint-types-test (ui)` | `scripts/check-module packages/ui`, the same commands as kit-ts, with Node only and no Valkey or Postgres, which its tests do not use. |
| `integration (kit)` | Passes when both kit jobs, `lint-types-test (kit-ts)` and `lint-types-test (kit-py)`, passed; it does not wait for ui. The kit-ts and kit-py integration tests run there, against the Valkey and Postgres from the Compose stack (`deploy/compose.yml` + `deploy/compose.test.yml`): the bus and tenant streams on Valkey, and row-level security on Postgres (as a plain app role, because a superuser bypasses RLS). It runs even when a kit job fails or is cancelled and then fails, because a skipped required check counts as passed. |
| `modules` | Passes when every module job passed. One `module (<name>)` job runs per `modules/<name>` that has checks: lint, types and unit tests, plus its Postgres and Valkey tests against the Compose services, through `scripts/check-module`. A new module needs no `.github/` change. See [modules](#modules). After it first runs on main, a maintainer adds `modules` to the required checks. |
| `compose (deploy)` | Fails first unless `modules` passed, so the module checks (the RLS and cross-tenant leak tests among them) block merges through this required check even before the ruleset lists `modules`; it waits for them. Then it makes a fresh `CANCCU_SECRETS_KEY` and each module's own fresh secrets, starts the whole stack with `docker compose -f deploy/compose.yml up --build --wait`, and checks the platform-wide rules: that only Caddy publishes a port, that only the five named volumes exist (the three for data, `deploy-status`, which only the host's auto-deploy writes, and `render-socket`, the only way into the isolated renderer), that hello's health through Caddy is `ok`, that health is `503 down` when Valkey stops, and that hello refuses to start without a kit variable. Between the health and Valkey checks it runs every module's own stack smoke checks. See [compose](#compose). |
| `demo-stack` | From `.github/workflows/demo-stack.yml`: passes when every job its [tier](#tiers) needs passed and the others were skipped. Those jobs start the whole stack with the demo event (`deploy/compose.yml` + `deploy/compose.ci.yml`, images from the layer cache, fresh secrets as in `compose (deploy)`), run the API tests (`scripts/demo-stack-test`), the player's soak, and the screenshots (`scripts/demo-screenshots`) in shards, merged into the artifact `demo-screenshots`. See [demo-stack](#demo-stack). |
| `no-event-names` | Fails if the lines a PR adds contain a forbidden term. |
| `review-gate` | From `.github/workflows/review-gate.yml`: passes only on an independent review's `Review verdict: pass <head sha>` for the PR's current head (see below). |
| `contracts` | `scripts/check-contracts`: validates every `events/*/profile.yaml` against `contracts/profile.schema.json` and every `events/*/themes/*/theme.yaml` against `contracts/theme.schema.json`, checks the paths they name exist (for themes with `scripts/check-theme-refs`, which also checks ids, grid areas and references, and runs its self-test), and lints `contracts/*.openapi.yaml` with Redocly (`contracts/redocly.yaml`), each one with its parts (`contracts/<module>/*.openapi.yaml`). |
| `setup (self-test)` | Runs `setup/test.sh` (no root, never changes the host: every script with `--dry-run` or against an unreachable daemon) with a pinned, checksummed ShellCheck release (the job's `SHELLCHECK_VERSION` and `SHELLCHECK_SHA256`, updated together in a PR of their own), jq and the docker CLI and daemon present, and fails if any check is skipped except `systemd-analyze verify`, which the runner may lack. Covers `setup/` and the Caddy ports and network in `deploy/compose.yml`. After it first runs on main, a maintainer adds it to the required checks. |
| `naming` | `scripts/check-naming`: fails if a tracked file name or line uses the old platform prefix as an identifier ([ADR 0017](decisions/0017-naming.md)). After it first runs on main, a maintainer adds it to the required checks. |
| `tenancy` | `scripts/check-tenancy`: every table in `modules/*/migrations/*.sql` is a tenant table with `tenant_id`, row-level security and a tenant policy, tenant-scoped keys and composite foreign keys, unless `scripts/tenancy-global-tables.txt` lists it; module source spells no raw Valkey key or stream name. See [tenancy](#tenancy). After it first runs on main, a maintainer adds it to the required checks. |
| `file-size` | `scripts/check-file-size`: warns, and never fails, on tracked source files over 400 lines (the file-size rule, AGENTS.md) and OpenAPI contracts over 1,500. Not a required check. |

Do not rename these jobs; renaming breaks the required checks.

## modules
- **The runner:** `scripts/check-module [--dry-run] <module> [ROOT]` runs the checks of `modules/<module>` (`packages/<name>` runs those of a package, for the `lint-types-test` jobs) and stops at the first one that fails (exit 1; exit 2 on wrong usage, an unknown module or a module without checks). `scripts/check-module --list` prints the modules that have checks as a JSON array, which the `modules (list)` job hands to the matrix. `scripts/check-module --needs <module>` prints what its CI leg sets up, as `node=`, `python=`, `postgres=` and `valkey=` lines (`true` or `false`). Self-test: `scripts/check-module --self-test`.
- **What runs** is chosen from the module's files, so a new module gets its checks by following the convention:
  - an executable `check` file in the module: that alone, from the module folder. For checks the plain runner cannot run, for example inside the module's own image.
  - otherwise, with a `package.json`: `npm ci` in each local package it uses (`file:../../packages/<name>`, built by its `prepare` script), then `npm ci`, `npm run lint`, `npm run typecheck` and `npm test`.
  - with a `pyproject.toml`: `pip install -e ".[dev]"`, `ruff check .`, `ruff format --check .`, `mypy .` and `pytest`. A module with both files runs both sets.
  - A module folder with none of these (a placeholder) has no checks and gets no job.
- **One setup** (#302): every `module (<name>)` and `lint-types-test (<package>)` job checks the repo out and runs `.github/actions/check-module`, so the two kinds of job cannot drift apart. The action asks `scripts/check-module --needs` what the checks use and sets up only that:
  - Node 22 for a `package.json`, Python 3.12 for a `pyproject.toml`; a module with its own `check` sets up its own toolchain (screen-render builds its image).
  - Postgres when a file under the module's `test/` or `tests/` (or its own `check`) names `CANCCU_DATABASE_URL`, Valkey when one names `CANCCU_VALKEY_URL`, each started from the Compose stack (`deploy/compose.yml` + `deploy/compose.test.yml`). In Postgres it creates the database `canccu_test`. So a test that reads one of the URLs lives under `test/` or `tests/`: a colocated `src/**/*.test.ts`, or a root `conftest.py` or `vitest.setup.*`, would get no service and fail on a refused connection.
  - It sets `CANCCU_VALKEY_URL` and `CANCCU_DATABASE_URL` (the superuser, on `canccu_test`) on every job, even without the service, so tests that skip without a database run in CI, and a test the probe missed fails on a refused connection instead of skipping. Each job has its own Postgres, so a module's tests may drop and recreate their tables. On a failure it prints the services' logs.
- **Test databases only:** the module tests that drop or empty tables (screen, theming, agenda, notify, tenants and admin's settings store) first ask the server for its database's name and refuse to run unless it ends in `_test`, before they migrate, drop or empty anything: through the kit's `requireTestDatabase` (kit-ts, `@canccu/kit/testing`) or, in kit-py (`canccu_kit.testing`), `require_test_database_url` before the store connects, because a module's `Db.connect` already runs its migrations, some of which drop tables. A new module whose tests drop or empty tables calls it too.
- **The required check** is `modules`, never the per-module names, which come and go with the modules. It runs even when a module job fails or is cancelled and then fails, because a skipped required check counts as passed. The required `compose (deploy)` job needs it and fails unless it passed, so the module checks block merges even while the ruleset does not list `modules`. Do not rename `modules`.
- **Locally:** point `CANCCU_DATABASE_URL` at a throwaway test database whose name ends in `_test`, never at the Compose database `canccu` you keep: the tests drop, recreate and empty their tables, and refuse any other name. With the Compose Postgres, make the test database once next to `canccu` and use it:

  ```sh
  docker compose -f deploy/compose.yml -f deploy/compose.test.yml up -d --wait valkey postgres
  docker compose -f deploy/compose.yml exec postgres createdb -U canccu canccu_test   # once
  export CANCCU_VALKEY_URL=redis://127.0.0.1:6379
  export CANCCU_DATABASE_URL=postgres://canccu:canccu-local-only@127.0.0.1:5432/canccu_test
  ```

  Use your own `POSTGRES_PASSWORD` if `deploy/.env` sets one, or a throwaway container instead (see [modules/screen/README.md](../modules/screen/README.md#check)). Then run `scripts/check-module <module>` (inside a Python virtual environment for a Python module).

## compose
- **Module stack smoke checks** (#324): a module checks itself against the running stack in its own `modules/<name>/ci/stack-smoke.sh`, never in `.github/workflows/ci.yml`, so a module PR touches only its module. `scripts/stack-smoke run` runs every such script in module-name order, from the repo root, with `CANCCU_SMOKE_BASE_URL` (default `http://127.0.0.1`, an IP literal, so IP mode serves the demo tenant) and `CANCCU_SMOKE_COMPOSE_ARGS` (default `-f deploy/compose.yml`). A script prints what it checks and exits non-zero on a failure; the runner goes on with the rest and then fails, naming every module that failed. A module that needs secrets on the stack has a `ci/stack-env.sh` that prints `CANCCU_NAME=value` lines of fresh random values, never a fixed key; `scripts/stack-smoke env` collects them (refusing any other line) and CI appends them to `$GITHUB_ENV` before the stack starts, here and in `demo-stack`. `scripts/stack-smoke --self-test` tests the runner. Locally: start the stack, then `scripts/stack-smoke run`.

## demo-stack
- **Stack:** `docker compose -f deploy/compose.yml -f deploy/compose.ci.yml up -d --build --wait`. The CI overlay adds three things, and is never used for a real install:
  - A second event, `demo-two` (CI data only, written by `tenant-two-seed`), so the screen load test drives screens of two events. IP mode serves the demo tenant only while it is the only tenant ([0013](decisions/0013-multi-tenant-core.md) item 2), so on this stack both events answer on hostnames: the platform domain is `localhost`, the demo event is `demo.localhost` and the second `demo-two.localhost`. The scripts still take Caddy's address (`http://127.0.0.1`) and name the event in `Host`; Chromium resolves `*.localhost` to the loopback itself. `CANCCU_DEMO_HOST` overrides the demo event's hostname.
  - `event-seed` copies `events/demo/` into the demo tenant's event folder of the files volume (`/files/demo/admin/event`), owned by the modules' user 65534 ([setup/README.md](../setup/README.md#files-volume)), after `files-init` and before admin starts.
  - `session-stub` stands in for Discord sign-in, which CI cannot run: the rights checks of admin, screen, theming, agenda and notify (the kit's, through `CANCCU_ADMIN_URL`) ask it for `GET /api/admin/session`. The cookie `canccu_session=demo-ci` is a session with every admin right, screen's content, device (read, pair, write; reading a zone's screens is also what the Theme studio's screen preview needs), zone and ticker rights, and the rights the screenshots' pages need (the three theming rights an event admin holds, `theming.theme.write`, `theming.embeds.write` and `theming.sync.write`, so the Studio shows an event admin's view; `agenda.items.write`, `agenda.crew.read`, `notify.topics.write`, `notify.stats.read`, `notify.checkin.display`); any other cookie gets 401 `not_signed_in`. Every other path goes on to admin, so the modules still read their settings there. Compose does not recreate the stub when only its config changes: after changing it, `up --force-recreate session-stub`. Admin's real session API still answers through Caddy, and the tests check it.
- **API tests:** `scripts/demo-stack-test [--dry-run] [--only LIST] [BASE_URL]` (curl, jq, python3; `--only` runs the platform smoke and the tests of the listed modules, `all` for every module's, `soak` for the soak, see [Tiers](#tiers); without it, everything): health of hello and admin through Caddy, and of every module (#461), 401 without a session (also from admin's own `GET /api/admin/session`), the sign-in page, Load from the seeded event folder, profile import and export as a zip, settings read, save and `409 version_conflict`, `404` for an unknown module, the health view, a file uploaded through screen and read back through Caddy byte for byte (the files volume is writable, #286; the bytes are new each run, so a reused volume proves it too), and agenda's and notify's prefix routes (the bare prefix redirects with its query; the internal paths, the API and health under it are 404), the push channel's latency (`modules/screen/test/stack/push-latency.mjs`, run in the screen container through `CANCCU_DEMO_COMPOSE`: a paired screen's stream gets 20 ticker changes, p95 under 1 s), that the second event answers on its hostname, the screen load test (`load.mjs`, in the screen container: 50 screens in each event, 10 ticker changes per event, every screen gets each change, p95 of all deliveries under 1 s, no screen sees the other event's ticker) and the player's accelerated soak (`scripts/screen-soak --hours 24 --minutes 6`: Chromium from the Playwright image in the screen container's network namespace plays a paired screen while a fake clock runs 24 hours, and its heap after GC may grow at most 8 MiB after the first hour; see [modules/screen/README.md](../modules/screen/README.md#soak-and-load)). It ends by importing the demo event again, so the screenshots show it. Hand-written for now; tests generated from `contracts/` come later.
- **Screenshots:** `scripts/demo-screenshots [--dry-run] [--groups LIST] [--check] [BASE_URL] [OUT_DIR]` (`--groups` and `--check`: see [Tiers](#tiers)) takes Chromium screenshots of every user-facing surface, a fixed list (#376), so a user-visible PR's reviewer finds its views there and holds them against the mockups (AGENTS.md, A package run): the admin pages (`/admin/settings`, `/admin/settings/admin`, `/admin/health-view`, `/admin/profile`), the Theme studio (advanced, history; then, after the screens, so its screen preview draws the main zone's Pulse with the fixture's run of show, which the shot waits for: the brand kit at both widths, then with a draft of mockup 12's brand and the demo logo at both widths, its Advanced page and its screen preview at full size, then light, with the warning Publish opens, at both widths, `studio-draft*.png`, discarded afterwards; its phone pages are shot with the window as tall as the page, so the bottom bar sits at its foot) and the phone hub's preview, the agenda pages (the run of show's empty state; after the fixture fills a day, its day view at both widths and at 1440 px, which waits for the main zone's live miniature, an item a row picks, and the delay confirm a chip opens over the day, at both widths; new item, quick add, and an item's Delay page, with the items after it and quiet, and its Edit form, on items the run adds through the agenda's API and removes afterwards), notify's topics page, the check-in page of a fresh arrival code, and the Screen studio (Live, Devices, the pair dialog a kiosk's QR opens, Zones, the zone editor with a preview drawn, and Ticker, at both widths, and Devices at 1440 px for its Recent panel; then, while the hall screen plays, a preview on a screen (`preview-shots.mjs`): the zone editor's dialog and its notice at both widths, the hall screen with its Preview mark, and the Theme studio's dialog and notice on a draft made for it, all removed afterwards; shot after the screens, on the demo fixture with a landscape and a portrait screen paired, so its live views draw the Pulse, and a Studio live view that draws no run of show within 30 s fails the check), full page, at 1280×800 or, for phone pages (`*-phone.png`), 390 wide and 844 or the page's full height if taller, so the bar and any sticky action row sit where they do at the end of the page; and the screens (#191, `modules/screen/test/stack/screens.mjs`): every demo theme on the Pulse with the identify card, the offline marker and the device frames that follow a theme (not assigned, archived), the default theme at 1920×1080 and 3840×2160, landscape and portrait, the others at 1080p, plus the frames drawn before a theme (pairing, refused, moved, unreachable, the kiosk check), the claims of mockup 04, a photo in the hero and the entrance zone with the check-in QR, each named as the view it shows (`theming-<theme>-screen-<view>-<w>x<h>.png`). The screens play the demo fixture (`fixture.mjs`: a run of show around now over two days with a running and a delayed item, which `day.mjs` keeps on the event's date at any hour of the run, a ticker line, a main and an entrance zone); a state the stack cannot reach (refused, moved, archived, a claim) is the page's own answer to a device answer or a state it is handed. The lists and the browser run are `scripts/demo-screenshots.mjs` and its group files `scripts/demo-screenshots-*.mjs` (`playwright-core`, one Chromium), which pairs the screen with the stack client of the screen tests (`modules/screen/test/stack/client.mjs`). Pages are signed in with the stub's cookie; a page that does not answer 200 itself (signed out, a page sends the browser on to the sign-in page) or whose API reads answer 401, 403 or 5xx fails the check, and so does a screen view that does not draw within its wait, or whose text does not read from across a hall: the readability check (`readability.mjs`, its rules held by `modules/screen/test/stack-readability.test.ts`) fails any text under 2.5 % of the screen's short side and any text below the theming contract's contrast rules on a ground under it. Afterwards the screens are revoked and the event's open pairing codes are cleared; a failed cleanup fails the check too. A second pass (`scripts/demo-screenshots-front.mjs`, #440, #437, #441) follows, after `scripts/demo-screenshots-front.sql` seeds what no API of the CI stack makes (people who signed in, a session without a role, and events archived, starting in three days and away from their venue): the sign-in page's states, the offline page, People with 40 people, a role change's Undo, Remove's confirm and the person sheet, every check-in state, and the archived event's run of show (with an item the seed adds) and Screen studio, read-only (#439); each shot must also show its state's words. A new user-facing page joins its group's list (see [Tiers](#tiers), A new page). It runs in Playwright's image `mcr.microsoft.com/playwright:v<version>-noble` (the same version as the browser tests), which ships Chromium and its libraries, so the step needs no apt and an Ubuntu mirror outage cannot fail it (#378). The image joins the network namespace of the stack's Caddy container (found through `CANCCU_DEMO_COMPOSE`, as for the API tests), so `BASE_URL` is Caddy's address as seen from inside that container (default `http://127.0.0.1`; a remote or host-published address does not work), and the browser comes from the loopback, an address of the demo venue, which the venue IP check needs before a screen pairs or plays. The pages open on the demo event's hostname (`CANCCU_DEMO_HOST`, default `demo.localhost`) at `BASE_URL`'s port, and the API calls name it in `Host`. `scripts/demo-screenshots --install` pulls that image (CI). The PNGs are the artifact `demo-screenshots` of the run (kept 14 days; `gh run download <run> -n demo-screenshots`); on failure the Compose logs are the artifact `demo-stack-logs`.
- **Locally:** start the stack as above, then `scripts/demo-stack-test` and `scripts/demo-screenshots` (needs Docker, for the image; for another Compose project or extra files, set `CANCCU_DEMO_COMPOSE` to its compose command). Stop with `docker compose -f deploy/compose.yml -f deploy/compose.ci.yml down -v`.
- **Required check:** `demo-stack` is in the required checks of the main ruleset (#4). Do not rename the job; it is the aggregator of the [tiers](#tiers), so the jobs it needs may change without a ruleset change.

## Tiers
`demo-stack.yml` (#461) first runs `demo-stack (plan)`: `scripts/demo-stack-plan.mjs` (with `--self-test` first, in `scripts/demo-stack-plan-test.mjs`) reads the event and, for a pull request or a merge-queue entry, the changed paths, and picks a tier. The path map is `scripts/demo-screenshots-groups.mjs`, next to the screenshot script: first match wins, and a path no line matches is the full run.

| Tier | Paths | Runs |
|---|---|---|
| docs | only `*.md`, `docs/`, `contracts/` (ADRs among them) but the contract files an image reads at runtime (`profile.schema.json` admin's, `theme.schema.json` theming's, `flags.yaml` tenants'), which count as their module's | no stack; `demo-stack` passes in seconds |
| module | `modules/<name>/` of modules that are not shared | `demo-stack (api)`: `scripts/demo-stack-test --only <the changed modules>` (tenants' tests are admin's, screen-render's screen's: the stack test has none of their own; it refuses a `TAGS` list out of step with `TESTS`), the platform smoke (every module's health through Caddy, the sign-in page and sessions, the demo event imported, the second event, one organiser page of each module) and those modules' tests; `demo-stack (soak)` when screen changed; `demo-stack (shots <shard>)` for the screenshot groups of the changed modules only |
| full | `packages/`, `deploy/`, `events/demo/`, `modules/theming/`, `modules/screen/player/`, `modules/screen/test/stack/`, the workflow, its action and the `scripts/demo-*` and `scripts/screen-soak` scripts, and any path the map does not know | every API test, the soak and every screenshot shard |

- **Screenshot groups and shards:** a shot belongs to the module that serves its page, found from its path (`/admin/screen/` the Screen studio, `screen-studio`; `/admin/` admin; `/agenda/`, `/notify/`, `/theming/`; `/screen/` the screens, `screens`). Each module's line of the map names the groups it needs (admin and tenants: `admin`; agenda; notify; screen: `screens` and `screen-studio`; screen-render: `screens`; a module without pages: none). Three shards, each with a stack of its own, run in parallel: `pages` (admin, agenda, notify, theming, with the front and trouble passes), `screens` (every theme's screens) and `studio` (the Screen studio). A shard runs only the groups the tier picked, and a pass with no shot in them is skipped. The shards upload `demo-screenshots-<shard>`, which `demo-stack (screenshots)` merges into the one artifact `demo-screenshots`, also when a shard failed. Together the shards take exactly the shots of one run of every group (the planner's self-test checks it): a shard without the screens publishes the demo themes as the screens would, so the studios look the same.
- **Merge queue:** the tier of the queue entry's changes, with the screenshots in check mode (`--check`): every page check and readability check of the stack tests in `modules/screen/test/stack`, but the screens at 1080p only, no 4K, no PNG of a page and no artifact. The screens still take their shots: they pace the views of a screen, which did not draw in time without them.
- **Full run:** on push to main, nightly (02:17 UTC) and by hand (`gh workflow run demo-stack.yml`, the screenshot book at a checkpoint): every surface, every theme and size; the artifact is `demo-screenshots`.
- **Faster when it runs:** each stack job builds the module images with Buildx and the GitHub Actions layer cache (`.github/actions/demo-stack-up`; the scopes are `release.yml`'s, one per module, so main's images are every PR's cache), and keeps the Playwright image in the Actions cache.
- **A new page:** its shots join the list of its group (`scripts/demo-screenshots-pages.mjs` for a page at one URL, `-agenda.mjs`, `-theming.mjs`, the screens' and Screen studio's in `modules/screen/test/stack/`, or the front pass), in the order `scripts/demo-screenshots.mjs` keeps; a page under a new path prefix, or a new module with pages, also gets its line in `scripts/demo-screenshots-groups.mjs` (AGENTS.md, A package run).

## Images
- `.github/workflows/release.yml` builds one image per module that has a `modules/<name>/Dockerfile`, from the repo root as in `deploy/compose.yml`, as `ghcr.io/<owner>/<repo>/<module>` in lowercase (`ghcr.io/tammilanit/canccuplatform-next/<module>`).
- **Push to main** pushes the tag `dev`. **A release tag** `v*` (for example `v0.1.0`) pushes the images with that tag. A pull request that changes the workflow or a module's Dockerfile builds the images without pushing them. A module without a Dockerfile is skipped.
- It logs in with the workflow's `GITHUB_TOKEN` (`packages: write`, only in the image job); no other secret. Build layers are cached in the GitHub Actions cache per module.
- **First push:** GHCR creates each package on its first push and links it to this repo through the `org.opencontainers.image.source` label. The packages stay private (the product owner, 2026-11-08): each host that pulls them needs root's registry login with a read-packages token, renewed when it expires ([setup/README.md](../setup/README.md#auto-deploy), Set up auto-deploy, step 3).
- These are not required checks: they run after merge.
- **Auto-deploy:** a host in dev mode pulls the `dev` images and deploys them once every image's `org.opencontainers.image.revision` label is the new main commit (`setup/deploy`, see [setup/README.md](../setup/README.md#auto-deploy)).

## contracts
- `scripts/check-contracts [--dry-run]`; tools come through `npx` with pinned versions (ajv-cli, ajv-formats, @redocly/cli), so it needs Node 22 and no `package.json`.
- Fails (exit 1) on an invalid profile, a missing asset, an invalid theme package (schema, files or references), a failing `check-theme-refs` self-test or an OpenAPI lint error; exit 2 on wrong usage or missing files.
- **Required check:** after this job first runs on main, a maintainer adds `contracts` to the required checks of the main ruleset. Do not rename the job.

## naming
- `scripts/check-naming [DIR]` scans every tracked file (names and contents) of the repo, or of `DIR`, for an identifier with the old prefix: the uppercase prefix followed by `_` or `-`, the lowercase one followed by `_` or `-` and a letter, a template `$` or a regex `[`, or the old npm scope. Exit 1 lists `file:line`; exit 2 on a broken run.
- Exempt: `docs/plans/` (history). The coreutils `cp` command never matches, because a space follows it; neither do longer words such as `scp-`.
- Self-test: `scripts/check-naming --self-test`.
- **Required check:** after this job first runs on main, a maintainer adds `naming` to the required checks of the main ruleset. Do not rename the job.

## file-size
- `scripts/check-file-size [DIR]` scans every tracked source file of the repo, or of `DIR`, and warns on each one over 400 lines, and on each `*.openapi.yaml` over 1,500 lines ([contracts/README.md](../contracts/README.md#shared-components)): a `file:line` line locally, a `::warning` annotation on the file in Actions. It exits 0 whether or not it warns, so the job never fails on a long file; exit 2 only on a broken run (not a git work tree). The self-test step does fail the job, because a failing self-test means the checker itself is broken.
- **Source:** files ending in `.ts`, `.tsx`, `.js`, `.jsx`, `.mjs`, `.cjs`, `.py`, `.sh`, `.bash`, `.css`, `.scss`, `.html`, `.svelte`, `.vue` or `.sql`, and files without an extension that start with `#!`. Docs, data, lockfiles and config are not source; OpenAPI contracts have their own limit.
- **Exempt:** generated files, marked by `@generated` or `DO NOT EDIT` in their first five lines, and the entries of `scripts/file-size-exemptions.txt`: one `<path or glob> <reason>` per line, where `*` also matches `/`. An entry without a reason is reported and exempts nothing. The health pass reviews the list ([0019](decisions/0019-work-packages.md)).
- Self-test: `scripts/check-file-size --self-test`.
- Not a required check: it only warns. Do not rename the job.

## tenancy
- `scripts/check-tenancy [DIR]` (Python 3, no packages) reads every tracked `modules/<module>/migrations/*.sql` in name order, per module, and every module source file under `modules/<module>/src/` ([0013](decisions/0013-multi-tenant-core.md) items 5–7).
- **A tenant table** (every table not on the allow-list) needs: a `tenant_id` column; `ENABLE` and `FORCE ROW LEVEL SECURITY`; a `CREATE POLICY` for all commands (no `FOR`, or `FOR ALL`) on the kit's tenant setting (`current_setting('canccu.tenant', …)`), and no permissive policy without it, because Postgres ORs permissive policies (an `AS RESTRICTIVE` one only narrows); `tenant_id` in its primary key, every unique constraint and every unique index; and foreign keys composite with `tenant_id` on both sides, except a plain reference to a global table of the same module. `DISABLE` or `NO FORCE ROW LEVEL SECURITY`, `DROP POLICY`, dropping `tenant_id` and `DROP CONSTRAINT` on a tenant table fail, with one exception: a plain `DROP CONSTRAINT <name>` (no `CASCADE`) of a CHECK passes when the same migration file then adds a CHECK of the same name back to the same table with `ADD CONSTRAINT <name> CHECK (…)`, so a migration can widen a CHECK. The reader knows a name as a CHECK only if it never saw that name on anything else: a `CONSTRAINT <name> CHECK` or an unnamed column CHECK (Postgres names it `<table>_<column>_check`); an unnamed table-level CHECK is not known, so dropping it fails. A name the reader saw on a key, foreign key or `USING INDEX`, a name an index was renamed to (that renames the key behind it), and a name of the shape Postgres gives an unnamed key (`…_pkey`, `…_key`, `…_fkey`, `…_excl`, with or without a number) are never known as a CHECK. A drop is reported in the migration that made it. The kit writes the column and the policy for you: `TENANT_COLUMN_SQL` and `rlsSql(table)` (kit-py: `rls_sql`).
- **Global tables** are listed in `scripts/tenancy-global-tables.txt`, one `<module> <table> <reason>` per line; an entry without a reason is reported and exempts nothing. A new global table needs a change to that list, so the review sees it.
- **No raw keys:** a string literal in module source starting with `events:` or `t:` fails; modules use the kit's `tenantStream`, `platformStream` and `tenantKey` (kit-py: `tenant_stream`, `platform_stream`, `tenant_key`). In TypeScript and JavaScript a literal starting with a module's name and `:` (for example `"screen:render:ring"`) fails too: a key that spans every event comes from `platformKey`. kit-py has no counterpart yet, so Python source is not checked for these.
- **Limits:** the SQL reader understands `CREATE TABLE`, `ALTER TABLE` (a `RENAME TO` carries the table's checks to its new name, also through `ALTER INDEX`, which Postgres lets rename a table; a `RENAME CONSTRAINT` carries the constraint's kind), `CREATE [UNIQUE] INDEX` and `CREATE POLICY`; DDL built at runtime in code is invisible to it, so modules keep their schema in migration files.
- Exit 1 lists `file: problem`; exit 2 on a broken run (not a git work tree). Self-test: `scripts/check-tenancy --self-test`.
- **Required check:** after this job first runs on main, a maintainer adds `tenancy` to the required checks of the main ruleset. Do not rename the job.

## no-event-names
- `scripts/check-event-names [--dry-run] [BASE]` scans added lines of `BASE...HEAD`, case-insensitively.
- The term list (event name, venue, IPs, hostnames, Discord ids) is **not in the repo**. A maintainer stores it in the Actions secret `EVENT_NAME_TERMS`, one term per line or comma-separated.
- Exempt: `github.com` git remote URLs (https, ssh, `git@`) and `<org>/<repo>` slugs of this org. Nothing else: the bare org name in prose, or its domain in a hostname or URL, still fails when it is on the term list.
- The log shows only `file:line`, never the matched term.

- Without the secret the check fails (exit 2), except on fork PRs, where secrets are unavailable and it is skipped with a warning; a maintainer reviews those when approving the run.

## Code review
- There is no `claude-review` check any more. It ran Claude in CI on a subscription token that can no longer be renewed, so `.github/workflows/claude-review.yml` and its prompt `.github/claude-review.md` were removed.
- In its place every PR gets an independent review outside CI. A separate reviewer that did not write the change runs the review: in Claude Code, a fresh session with `/code-review` at `high` effort, plus `/security-review` for code or config for sign-in, rights, sessions, secrets or tenancy/RLS. It posts, as the reviewer identity (see review-gate), a PR comment whose last line is `Review verdict: <pass|changes|manual — reason> <head sha>`. Neither the author nor the reviewer enables auto-merge: the dispatcher (the maintainer tooling) does so after `review-gate` passes, for PRs that need no maintainer's accept, or a maintainer does. A maintainer arranges the review for fork PRs. See AGENTS.md, A package run (step 8) and Merge rules.
- **Required check:** a maintainer removes `claude-review` from the required checks of the main ruleset before the removal merges; otherwise every PR waits for a check that never runs.
- The secret `CLAUDE_CODE_OAUTH_TOKEN` is no longer used; a maintainer may delete it under Settings → Secrets and variables → Actions.

## review-gate
- **Reviewer identity:** the gate trusts verdicts from one account only: the login in the repository variable `REVIEWER_LOGIN`. This is a dedicated reviewer bot account, and author sessions do not hold its token. Independent reviews post their verdict comment as that account; authors never post verdict lines, and comments by anyone else (maintainers included) are ignored. `author_association` is not used: the Actions token reports privately listed org members as `CONTRIBUTOR`.
- **Setup:** a maintainer sets `REVIEWER_LOGIN` under Settings → Secrets and variables → Actions → Variables, and gives the reviewer account the access it needs to comment on PRs (it does not enable auto-merge). Its token stays with the reviewer sessions or the maintainer tooling, never with author sessions and never in the repo. While the variable is unset, the gate fails with a message that says so. The variable may not be available to fork runs; there, the gate fails, and the maintainer who approves the run re-runs the check.
- **Rule:** among the reviewer identity's comments, the newest one that contains `Review verdict:` anywhere, or that has been edited, decides. The check passes only when all of these hold:
  - the comment was never edited (`updated_at` equals `created_at`);
  - its last line fully matches `^Review verdict: (pass|changes|manual — .+) ([0-9a-f]{40})$`;
  - the verdict is `pass`;
  - the SHA equals the PR's current head;
  - the base branch has not changed since the comment was posted (no `base_ref_changed`, `base_ref_force_pushed` or `automatic_base_change_succeeded` event after it in the PR timeline).

  Otherwise the check fails and names the reason: no verdict, verdict comment edited, unparseable verdict line, `changes`, `manual`, a verdict for an older head, or a base change after the verdict. A newer verdict that is not the bare last line therefore fails the gate instead of letting an older `pass` decide: a footer after it, bold, backticks, a quote or indentation. Every comment the reviewer edits fails the gate too, verdict or not.
- **Edited verdicts do not count:** anyone with write access can edit another user's comment, and the comment keeps its author. So an edited verdict comment fails the gate with "verdict comment was edited; ask for a new review". The same happens when a verdict line is edited away. The reviewer posts a new comment instead of editing an old one.
- **A push voids a review:** the new head has a new SHA, so the old `pass` no longer matches, and the check fails until the reviewer posts a verdict for the new head.
- **Triggers:** `pull_request` (opened, synchronize, reopened, ready_for_review, edited) runs the check. `edited` covers a base-branch change, which keeps the head SHA; title and body edits only re-run the check. The `review-gate (rerun on verdict)` job handles PR comments by the reviewer identity:
  - It fires on created, edited and deleted comments that contain `Review verdict:`, on edits whose old body did, and on any edit of a reviewer comment. So a withdrawn verdict or an edited note re-runs the gate at once, instead of failing it later at an unrelated moment.
  - It re-runs **every** review-gate run of that PR for the current head (same SHA, branch and head repo, and the PR number when GitHub lists one), with `.github/scripts/review-gate-rerun`. A push and a body edit that land together start two runs for one head; the check job's concurrency group (one per PR, `cancel-in-progress`) cancels one of them, but GitHub still counts each run's check, so re-running only one left the other red and kept the PR out of the queue for good (#202). A passed run is re-run too, so a newer `changes` verdict turns it red.
  - It re-runs them one at a time, each after the previous one has finished: two re-runs at once share the concurrency group and cancel each other. A re-run that a newer run cancels is re-run again. It waits for a run still in progress (it may have read the comments before the verdict), and gives up after about 8 minutes with an error.
  - It skips a run that still waits for a maintainer's approval.
  - The rerun is needed because a comment run belongs to the default branch, so its own check would never appear on the PR.

  On `merge_group` the check passes, because the PR was gated before it was queued. Every other comment on any issue or PR only starts a skipped run, which is noise in the Actions list and nothing more.
- **Why its own workflow file:** the gate re-runs its whole workflow run after each verdict, and GitHub only re-runs a run once it has finished. In `ci.yml` that would mean waiting for the full demo stack; on its own, the run finishes in seconds. Keeping it separate also keeps comment events away from the other CI jobs.
- **Safety:** no secrets and no LLM. The check job's `GITHUB_TOKEN` only reads (`contents`, `issues`, `pull-requests`). The rerun job additionally has `actions: write`, which it uses only to re-run the gate. Comment text is matched with `jq` in `.github/scripts/review-gate` and never executed. The gate runs the PR's own copy of its workflow and script, so a PR could weaken its own gate. This is why changes under `.github/` need a maintainer's accept.
- **Locally:** `.github/scripts/review-gate --self-test` and `.github/scripts/review-gate-rerun --self-test` (offline: a fake `gh` stands in for GitHub; it covers the push-plus-body-edit case, a cancelled and a failed run, both re-run in turn and never at once). To evaluate a PR: `gh api --paginate repos/<org>/<repo>/issues/<pr>/comments | jq -s 'add' > /tmp/c.json`, `gh api --paginate repos/<org>/<repo>/issues/<pr>/timeline | jq -s 'add' > /tmp/t.json`, then `REVIEWER_LOGIN=<login> .github/scripts/review-gate /tmp/c.json <head sha> <head sha> /tmp/t.json`.
- **Manual check of the rerun** (after a change to it is on `main`): on a test PR, push a commit and edit the PR body within a few seconds, so two review-gate runs start for one head (one ends cancelled, the other fails: no verdict yet). Post `Review verdict: pass <head sha>` as the reviewer identity. The `review-gate (rerun on verdict)` run logs `Re-running review-gate run <id>` once per run, one after the other, and both runs then end green, as does the required check on the PR.
- **Comment trigger:** GitHub runs comment events only from the workflow file on `main`, so re-runs on a verdict start once this workflow is merged. Before that, re-run the check by hand.
- **Required check:** after the workflow first runs on main, a maintainer adds `review-gate` to the required checks of the main ruleset. Do not rename the job.
- **Known limits.** The maintainer tooling (the dispatcher) treats every `.github/` PR as needing a maintainer's accept, which covers the first limit:
  - **A PR runs its own gate.** The check runs the PR's copy of `review-gate.yml` and `.github/scripts/review-gate`, so a PR that changes them can make its own check green. Possible follow-ups: `pull_request_target` with a checkout of the base ref only, or CODEOWNERS for `.github/` with required code-owner review.
  - **Deleted reviewer comments.** Anyone with write access can delete the reviewer's newer `changes` comment, so an older `pass` on the same head decides again. Deletions show in the organization audit log. Only people with write access can do this; it is a maintainer-only risk.
  - **The merge queue does not re-check.** On `merge_group` the gate passes without looking: a `changes` verdict posted after the PR was queued does not stop the merge. Remove the PR from the queue by hand.
  - **The rerun lookup has edge cases.** For fork PRs GitHub lists no PR number on the run, so two PRs from the same fork branch and SHA cannot be told apart. Runs older than 30 days cannot be re-run, and the rerun job then fails. In both cases, re-run the check by hand or push a new commit.

## Fork and first-time PRs
- Settings → Actions → General → "Fork pull request workflows from outside collaborators" is set to *Require approval for all outside collaborators*. CI does not run on a fork or first-time-contributor PR until a maintainer approves the run; that maintainer also arranges the independent review.
